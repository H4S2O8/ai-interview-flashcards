## 当前精确症状（v2.5.4 实测，最重要的线索）

- `onReadyToPlay` 触发（就绪=是）、`play()` 返回 true（播放中=是）、`timeControlStatus = 2`（playing）
- 但 `currentTime` 恒为 0、无声 → **AVPlayer 在“播放”一个解码不出样本的东西**
- 缓存文件 `statSync().size` 与源 mp3 完全一致（大小对，内容存疑）

## 结案：真正的病因只有两个，都不在音频上

v2.5.8 实测**本地模式能正常播放**。所以音频文件、R2、写盘通道、AVPlayer、
音频会话 —— 全都是好的，从来就没坏过。真正坏的只有两处：

1. **v2.5.5 的文件头校验**：`readAsBytes*` 在真机 JS 侧取不到 length/下标，
   于是「读不出头」被当成「不是 mp3」，把好文件判死，缓存永远重下（v2.5.6 修）。
2. **定时器渲染**：`setInterval` 回调里的 `setState` 不触发重渲染，进度读数
   永远是 0（v2.5.8 修）。

**而「无声」这个贯穿七个版本的核心结论，本身就建立在第 2 条的假读数上。**
v2.5.4 那条「就绪=是·播放中=是·状态=2·时间恒 0·无声」里，前三项是真的
（播放器确实在放），第四项是渲染假象，第五项——大概率是用户在时间不动、
进度条不走的情况下做出的判断。查了七版的东西，可能一开始就在出声。

**教训**：诊断代码本身没被验证过时，它产出的每一条「症状」都不能当事实。
v2.5.7 加的「构建 / 轮询」两个计数器——用来验诊断器自己的——是整条链上
性价比最高的一次改动，早三版加上能省下四个版本。

### 遗留：在线模式

远程 URL 下 `onReadyToPlay` 似乎一直不触发，按钮 `disabled={!ready}` 恒灰
（v2.5.9 改成建好播放器即可按，AVPlayer 自己边缓冲边起播）。
默认音源已改回 local——本来就是「下一次、之后离线」的设计。

## v2.5.7 结论：「时间恒 0」是假象，误导了六个版本

实测 **构建=1、轮询=0**。

- **构建=1** → 播放器没有被反复重建，生命周期是干净的。
- **轮询=0** → `setInterval` 回调里的 `setState` **根本不触发重渲染**。
  而同一批 state 由 Button 动作和 `onReadyToPlay` 回调设置时是生效的
  （「就绪=是 / 播放中=是」都变了）。所以坏的只有定时器这一条通道。

**推论：从 v2.5.0 起报告的「进度条卡 0:00 / 时间恒 0」全都只是界面没刷新，
不能拿来证明播放卡住。** 歌词同步滚动（v2.4.0 的功能）同理也从没在真机上动过。
这条假线索至少误导了六个版本的判断方向。

文档里的依据（AVCaptureMovieFileOutput 进度计时器示例，代码注释里）：

```
// 自递归 setTimeout(脚本环境只保证 setTimeout/clearTimeout)。每 0.5s 读一次
```

而且它推 UI 用的是 `progress.setValue(...)` —— **observable，不是 useState**。
`index.tsx` 里作者早就这么写了（`dragX` / `tick`，还留了注释说明为什么），
只有 `article.tsx` 没做这个处理。

**框架事实（记牢，别再踩）**：
1. `setInterval` 不保证可用，用自递归 `setTimeout`。
2. **定时器回调里的 `setState` 不重渲染**；要更新 UI 必须走 `useObservable().setValue()`，
   并在 JSX 里读 `.value` 订阅。
3. Button 动作、`await` 之后的续体、AVPlayer 的桥接回调里，`setState` 是正常的。

**连带修掉的坑**：watchdog 是 `setTimeout` 里调 `setPhase("error")` —— 同样不重渲染。
v2.5.4 起「一直没出报错卡」多半就是这么来的，等于兜底机制一直是哑的。
v2.5.8 改推 `stallMsg` observable，在播放器卡片上挂橙色横幅。

## v2.5.6 结论：与音频文件无关

在线流式和本地缓存**症状完全一致**。两条完全独立的取数通道给出同一个结果，
说明音频数据本身没问题 —— 前六个版本一直在修错的东西。病灶在播放器 / 音频会话 /
输出路由层。

## v2.5.7：先让诊断本身可信

复盘发现之前的诊断行有三处在骗人，难怪判断一直跑偏：

1. **`状态=2` 可能是陈的。** `tcStatus` 只由 `onTimeControlStatusChanged` 更新 ——
   状态变一次报一次。播放器起播后又悄悄停下，回调不会再触发，界面上就永远挂着 2。
   现在 500ms 轮询直接问播放器要 `currentTime` / `duration` / `timeControlStatus` / `rate`。
2. **`sessionErr` 从 v2.5.1 起就在 `setSessionErr`，但从来没渲染过。**
   会话到底降级到哪一档、有没有报错，六个版本一次都没显示给用户看。现在上诊断行。
3. **从没回读过会话真正生效的 category。** 只知道 `setCategory` 有没有抛错。
   新增「会话」字段回读 `SharedAudioSession.category` / `categoryOptions`。

同时收掉两个从未验证过的前提：

- **播放器可能在被反复重建。** 这个框架的 `useEffect` 重跑语义没人验证过。
  「effect 重跑 → cleanup 里 `dispose()` → 立刻重建」能精确造出这套症状：
  每个实例活不过几十毫秒，就绪/播放中被某个实例置过 true，而被轮询的永远是新实例
  （所以时间恒 0），声音也来不及出来。且 cleanup 每次都 `clearTimeout(watchdog)`，
  **watchdog 永远不会触发** —— 正好解释 v2.5.4 起「无报错卡」。
  v2.5.7 改成每个 source 只建一次（ref 判重），收摊挪到 `[]` 的 cleanup。
  诊断行的**「构建」正常应恒等于 1**。
- **`setState` 从 `setInterval` 里调用可能不触发重渲染。** 若如此，「时间恒 0」
  就只是显示没刷新，播放其实在走 —— 那这条线索误导了六个版本。
  诊断行的**「轮询」计数**专门验它：数字不动 = 重渲染没发生。

另外按文档顺序改了三处调用：`await` 会话配置完成再 `setSource`（以前 `ensureAudioSession()`
不 await 就往下走，`setSource` 跑在会话配好之前）；`play()` 在 `onReadyToPlay` 里兑现
（文档所有例子都这么写）；显式 `defaultRate = 1`（没见过它的默认值）。

## v2.5.5 的假阴性（已定位并修掉）

报错括号里**是空的**：`文件头异常（，不是 mp3）`。`bytesToHex` 只有在
`Math.min(3, bytes.length)` 为 0 或 `NaN` 时才返回空串 —— 即真机上
`FileManager.readAsBytesSync(p).slice(0, 3)` 的返回值在 JS 侧**取不到下标和 length**。

所以 v2.5.5 报的是「读不出文件头」，不是「文件头不对」。它把一次 `written ===
buf.byteLength` 已经核对通过的下载判死了；`cachedFileOk` 用同一条读通道，于是缓存
永远判坏 → 重下 → 再判死，正好是「不管重试几次都一样」。

**结论：`readAsBytes*` 这条读通道在真机上不可用。**（写通道 `writeAsData` 大小对得上，
未见异常。）v2.5.6 起：读头一律走 `Data.fromFile(p).slice(0,4).toHexString()`，
且 `headIsMp3()` 返回三态 —— `null`（读不出）绝不当成坏文件。

**教训**：诊断代码本身也会骗人。任何「校验失败就阻断」的分支，都要先确认校验器读得到东西。

## v2.5.6 的主改动：绕开整条文件通道

`AVPlayer.setSource(filePathOrURL)` **文档第一个例子就是直接喂 `https://.../audio.mp3`**，
远程 URL 一直是支持的，前面五个版本没试过。R2 Worker 的 Range 已实测可用
（`206` + `content-range`），所以 v2.5.6 把音源默认切成在线流式，
`fetch → arrayBuffer → Data → writeAsData → 读回` 这条连挂 5 版的通道整条绕开。

本地缓存保留为第二音源，播放器卡片和出错卡片上都有一键切换，可直接做 A/B。
