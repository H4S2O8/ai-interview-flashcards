langchain第08集　LangChain4j 是什么？它和 Java 生态怎么集成？
============================================================

仁菜：欢迎回来，我是仁菜——西米露，冰的。
桑多涅：进度。
仁菜：还剩三周零五天啊。
桑多涅：那今天讲 LangChain4j。
仁菜：……我昨天回去就想问了。
桑多涅：问。
仁菜：这个有必要了解吗？我们全栈 Python 啊，一行 Java 都没有。
桑多涅：你面的公司呢。
仁菜：……不一定。
桑多涅：国内企业后端的存量，绝大部分是 Java。
仁菜：……哦。
桑多涅：要往里加 AI 能力的时候，没有人会为了这个把一整套跑了八年的业务重写成 Python。
仁菜：……所以是 AI 去迁就它，不是它来迁就 AI。
桑多涅：这是第一个理由——第二个理由跟语言没关系。
仁菜：那是什么呢。
桑多涅：这题不考类名——它考的是你说不说得出，一层抽象不能替你做什么。
仁菜：……不能替我做什么。
桑多涅：这个能力换到任何框架都成立——所以今天你就算一行 Java 都不写，这集也不白听。
仁菜：……好吧。那我先说我的理解？
桑多涅：说。
仁菜：它就是 LangChain 官方做的 Java 版本嘛。把 Python 的 API 翻译成 Java，让 Java 程序员也能写 Chain。
桑多涅：……
仁菜：……第一句又错了？
桑多涅：官方特意强调过，它不是 Java 移植版。
仁菜：诶？可是名字里就带着 LangChain 啊！
桑多涅：名字受它启发，仅此而已——API、内部实现、发布周期，三样全是独立的。
仁菜：那它到底是什么呢。
桑多涅：一套从 Java 习惯出发设计的 JVM 开源库。重视类型安全、POJO、注解、接口和依赖注入。
仁菜：……这几个词很 Java。
桑多涅：所以更准确的说法是，它吸收了 LLM 应用生态里的通用模式，而不是逐项复刻 LangChain。
桑多涅：这个区别为什么重要，你想过吗。
仁菜：……因为答错了显得没做过功课？
桑多涅：因为它解释了这个框架最有辨识度的那个能力，为什么长成那样。
仁菜：哪个能力呀。
桑多涅：AI Services。
仁菜：……听着像个服务层。
桑多涅：Java 开发者熟悉什么。
仁菜：接口、类型、服务层？
桑多涅：他们不熟悉什么。
仁菜：……在业务代码里到处拼消息数组和 JSON。
桑多涅：所以 LangChain4j 顺着 Java 的思维方式，把一次 AI 能力包装成一个可调用的服务接口。
仁菜：……原来是这样。
桑多涅：整个框架分两层——低层是自己组零件，高层是直接调一个装修好的服务台。
仁菜：低层有什么呢。
桑多涅：ChatModel、EmbeddingModel、ChatMemory 这些。要精细控制的时候直接操作模型、消息、Embedding 和存储。
仁菜：高层就是 AI Services 吧。
桑多涅：更关心业务接口的时候，用高层把这些零件组合起来。
仁菜：那我要是搜到 ConversationalChain 那种东西呢。
桑多涅：官方文档里旧式的 Chains 已经明确标成 legacy 了。
仁菜：……又是名字骗人！
桑多涅：新项目不要因为框架名字里有 Chain，就把它当主入口。这是这题的第一个坑。
仁菜：记下了。那第二个坑呢。
桑多涅：你先说，它凭什么值得引。
仁菜：因为它把 OpenAI 接口封了一层？少写点 HTTP 请求代码，换模型只要改个地址。
桑多涅：……太浅了。
仁菜：浅在哪儿呀。
桑多涅：你只看到了模型调用。ChatModel、EmbeddingModel、EmbeddingStore 是统一抽象。
仁菜：……那高层呢。
桑多涅：高层还有 AI Services、Tools、Chat Memory、RAG 和结构化输出。
仁菜：那正经的答法是什么呢。
桑多涅：它主要解决三类问题——第一类，供应商 API 不统一。
仁菜：嗯，用统一接口把常见模型和向量库接到相对一致的 Java API 上。
桑多涅：第二类，LLM 应用胶水代码太多。
仁菜：AI Services 把 Prompt、输出解析、Tools、Chat Memory 和 RAG 组装起来。
桑多涅：第三类，Java 工程接入成本。
仁菜：……这个我不会答。
桑多涅：官方生态能融进 Spring Boot、Quarkus、Helidon 和 Micronaut，复用依赖注入、配置、测试和监控体系。
仁菜：……不用另起炉灶。
桑多涅：对。那现在回到统一接口——它能抹平所有差异吗。
仁菜：……应该能吧？都统一了。
桑多涅：举个场景——公司今天试 OpenAI，明天因为数据合规改用云厂商模型，后天又要接本地 Ollama。
仁菜：直接调各家 SDK 的话……认证方式、请求对象、消息格式、流式回调、异常类型，全都不一样。
桑多涅：业务层会怎样。
仁菜：……很快长满适配代码。
桑多涅：所以框架先给这些能力找共同语言。聊天模型实现 ChatModel 或者 StreamingChatModel。
仁菜：嗯……文本向量化用 EmbeddingModel，向量数据的写入和搜索面向 EmbeddingStore。
桑多涅：具体厂商能力放进独立的集成模块，业务代码尽量只依赖核心接口。
仁菜：那最大的收益就是一行代码切换任意模型！
桑多涅：……不是。
仁菜：诶？
桑多涅：最大的收益是把变化关在适配层里。
仁菜：……有区别吗。
桑多涅：有。单元测试可以替换模型实现，试不同向量库的时候也不用推翻上层的 RAG 流程。
仁菜：……但换供应商本身还是有代价的。
桑多涅：因为抽象只能覆盖交集。
仁菜：交集之外是什么呢。
桑多涅：某个模型支不支持工具调用、支不支持原生 JSON Schema、能不能收图片、有没有思考内容、有没有特殊采样参数。
仁菜：这些都要查能力矩阵吧。
桑多涅：换完之后还有四样必须重新验证。
仁菜：……Prompt 效果？
桑多涅：Token 计算、限流、异常处理，还有评测基线。
仁菜：评测基线为什么也要重来呢。
桑多涅：你换了模型还拿旧基线比，那你比的是什么。
仁菜：……什么都不是。
桑多涅：所以这题不能吹成完全无锁定——说得出这一句，比背十个类名管用。
仁菜：那 AI Services 具体解决什么呀。
桑多涅：只做一次模型调用，手写几行 SDK 代码难吗。
仁菜：不难啊。
桑多涅：那什么时候开始麻烦。
仁菜：……业务要多轮对话、要工具调用、要知识检索、还要稳定字段的时候。
桑多涅：那时候开发者在干什么。
仁菜：不停地拼 Prompt、转消息、跑模型循环、反序列化输出。
桑多涅：AI Services 就是来收拢这些胶水代码的。开发者声明一个 Java 接口，框架在运行时提供代理实现。
仁菜：……代理实现。这个模式我好像见过。
桑多涅：很像 Spring Data JPA，或者 Retrofit。
仁菜：哦！就是我描述服务要暴露什么方法，剩下的它来。
桑多涅：它负责把方法参数变成消息，再把模型响应转换成方法返回值。
仁菜：那一次调用背后到底发生了什么呢。
桑多涅：入口只有一句 chat——你自己顺一遍。
仁菜：……代理先把方法参数组织成消息。
桑多涅：然后。
仁菜：……Retriever 补充知识库内容。
桑多涅：模型判断要查订单。
仁菜：就调 Tools——工具结果返回以后，模型接着生成答案。
桑多涅：会话之间怎么不串。
仁菜：MemoryProvider 用会话 ID 隔离上下文。
桑多涅：最后一步。
仁菜：……框架把模型输出转换成一个 Java 对象。
桑多涅：一句话进去，这一整条链路出来——这就是高层的意思。
仁菜：……这也太方便了吧！
桑多涅：那我问你，返回值是个 record，框架自动生成 Schema 并且解析成功了，是不是就没问题了。
仁菜：……解析成功了还能有什么问题呀。
桑多涅：解析成功只说明数据形状对得上。
仁菜：……形状。
桑多涅：金额对不对、权限够不够、订单状态是不是真的，形状一个都管不了。
仁菜：……所以确定性的业务校验不能交给模型。
桑多涅：这句你上一集也说过一遍了。
仁菜：……它一直在回来。
桑多涅：还有一个时效性细节——想用模型供应商原生的 JSON Schema 约束，不是打开就有。
仁菜：要怎么样呢。
桑多涅：要确认对应的 ChatModel 支持，并且显式启用。
仁菜：不支持的话会怎样呢。
桑多涅：框架可能退回到 Prompt 格式指令，那种方式的可靠性更弱。
仁菜：……退回去了它还不报错。
桑多涅：所以你得知道它退没退。最后再补一句工程习惯 —— 依赖版本别在多处手填。
仁菜：为什么呢。
桑多涅：核心包、模型集成和 Spring Starter 的版本会互相错位。
仁菜：那怎么办呀。
桑多涅：官方推荐用 bom 管版本，再从 Release Notes 里挑验证过的。
仁菜：……记下了。那 Tools 呢，我以为我这块已经懂了。
桑多涅：那你说说，Tools 是不是把数据库权限交给模型。
仁菜：不是！模型只负责生成工具名和参数，请求执行某个动作。
桑多涅：真正运行 Java 方法的是谁。
仁菜：应用程序啊。
桑多涅：框架把工具说明和参数 Schema 发给模型，再执行模型选择的方法，把结果作为工具消息交回去。
仁菜：一次调用里可能来回好几轮吧。
桑多涅：模型到工具，工具再回模型，直到拿到最终结果。
仁菜：这层自动循环是真的省代码啊。
桑多涅：省代码，不省安全边界——查订单要做什么。
仁菜：用户和租户校验吧。
桑多涅：退款。
仁菜：幂等和额度控制。
桑多涅：发消息。
仁菜：……审批和审计。
桑多涅：工具抛异常了呢。
仁菜：……直接把异常信息返回去？
桑多涅：堆栈、路径和敏感信息原样回传给模型，你猜它会不会在答案里复述。
仁菜：……会。
桑多涅：那句话你自己说。
仁菜：工具描述约束的是模型行为，服务端权限约束的才是真实能力。
桑多涅：……嗯。
仁菜：这句是第五集那句的兄弟吧。
桑多涅：是同一句。换了个说法而已。下一块 —— Chat Memory 等于聊天档案吗。
仁菜：不等于啊。
桑多涅：……这次这么快。
仁菜：因为前天刚被你问过一模一样的结构！
桑多涅：那你说，它保存的是什么。
仁菜：下一次要喂给模型的上下文——可以淘汰、压缩、注入。
桑多涅：完整聊天记录呢。
仁菜：是产品要展示、要审计的事实记录啊。两回事。
桑多涅：官方明确说过，它提供的是 memory，不替应用保存完整 history。
仁菜：常用实现有哪些呀。
桑多涅：按消息数淘汰的 MessageWindowChatMemory，按 Token 窗口淘汰的 TokenWindowChatMemory。
仁菜：默认存哪儿呢。
桑多涅：内存里——要持久化就实现 ChatMemoryStore 接到数据库。
仁菜：多用户怎么隔离呢。
桑多涅：用 MemoryId 和 ChatMemoryProvider，不能让所有用户共享同一个窗口。
仁菜：……这个我上周才踩过。
桑多涅：还有一条更容易漏——同一个 MemoryId 不应该被并发调用。
仁菜：并发了会怎样呀。
桑多涅：可能破坏 Chat Memory。而且分布式并发控制是应用的责任，框架不管。
仁菜：……那业务口里说的长期记忆呢。
桑多涅：结构化存进业务数据库，或者做成可检索知识再用 RAG 注入。
仁菜：……而不是把消息窗口无限撑大。
桑多涅：对。RAG 这块你熟，我只问边界。框架给的是什么。
仁菜：……积木？文档加载、解析、切分、Embedding、向量存储，然后在线检索和注入。
桑多涅：简单知识库怎么接。
仁菜：嗯，把一个检索器直接交给 AI Service，让它先找资料再交给模型。
桑多涅：要查询改写、多路检索、融合、重排呢。
仁菜：……那就得用 RetrievalAugmentor 把这些阶段组合起来。
桑多涅：来源只能是向量库吗。
仁菜：不是。全文搜索、Web 搜索、知识图谱、业务数据库都行。
桑多涅：那什么决定最终效果。
仁菜：……不是框架。是文档质量、切分策略、召回率、权限过滤、引用溯源和离线评测。
桑多涅：这句上一集你已经用八比二证明过了。接着讲集成。团队要接它，第一步看什么。
仁菜：……先背一遍支持列表？
桑多涅：先看团队原来用什么服务框架。
仁菜：……哦，这才是顺序。
桑多涅：已有 Spring Boot 服务，就继续沿用它的配置、依赖注入和监控体系。
仁菜：那声明的部分呢。
桑多涅：Starter 能自动创建常用 Bean，也能用注解声明 AI Service。
仁菜：有版本坑吗？
桑多涅：接入或者升级的时候，按项目的 Spring Boot 大版本选对应依赖。
仁菜：Quarkus 呢。
桑多涅：优先用 Quarkus LangChain4j。它复用核心抽象，再接进 Quarkus 的 CDI、构建期装配、原生镜像和开发工具。
仁菜：不是另一套框架吧。
桑多涅：不是。Helidon 和 Micronaut 也有集成，但普通面试不用展开版本和注解清单。
仁菜：那说什么呢。
桑多涅：说一句优先沿用团队现有的依赖注入、配置和监控体系，就够了。
仁菜：……剩下的时间留给边界。
桑多涅：学得挺快——那我问你，一次客服回答错了，先看什么。
仁菜：看最终文本？
桑多涅：一次调用可能已经经过了 RAG 检索、模型判断和工具执行。
仁菜：……那只看结果等于什么都没看。
桑多涅：顺着调用链往下。第一步。
仁菜：……检查送给模型的消息。
桑多涅：第二步。
仁菜：确认 Retriever 到底找回了什么。
桑多涅：第三步。
仁菜：看 Tool 的参数和结果吧。
桑多涅：第四步。
仁菜：……确认输入输出校验有没有拦住异常内容。
桑多涅：这四段的请求、响应、耗时和错误，靠 ChatModelListener 这类监听入口采集。
仁菜：那 Guardrails 是干嘛的呀。
桑多涅：在模型调用前后校验输入和输出——越界问题、Prompt Injection、格式错误、违反业务规则的回答。
仁菜：那有了它是不是就安全了！
桑多涅：……你听听你自己这句。
仁菜：……我又来了。
桑多涅：两条边界。第一，官方目前仍然把 Guardrails 和 AI Service Observability 标为实验性。
仁菜：……实验性。那能用在哪一层。
桑多涅：只适用于 AI Services，不能直接套在低层 ChatModel 上。
仁菜：第二条呢。
桑多涅：Guardrail 不是安全系统的替代品。
仁菜：……Prompt Injection 检测会漏报。
桑多涅：输出校验也替代不了业务权限——认证、授权、数据隔离、资金风控和审计，必须继续放在确定性的业务层。
仁菜：……这一集你说了三遍类似的话。
桑多涅：因为面试官也会问三遍。那最后 —— 什么时候适合用它。
仁菜：嗯……已有大量 Java 服务，想把 AI 能力嵌进现有系统的时候。
桑多涅：典型场景。
仁菜：企业知识库问答、带会话上下文的智能客服、从合同和简历里抽结构化字段、批量摘要和分类、让模型查订单或者建工单。
桑多涅：还有一类。
仁菜：……要在多个模型或者向量库之间做选型评估的项目。
桑多涅：它最适合哪种团队。
仁菜：……AI 是业务系统的一部分的那种。
桑多涅：为什么。
仁菜：因为领域服务、数据库访问、权限和审计都已经写在 Java 里了。直接注册成受控 Tools，比新增一个 Python 微服务再跨语言调用简单。
桑多涅：反过来，什么时候不该用。
仁菜：只调一家模型做一次文本生成的时候吧，官方 SDK 更轻。
桑多涅：还有。
仁菜：深度依赖某家刚发布的专属能力的时候，直接 SDK 更早暴露完整参数。
桑多涅：第三种最容易被忽略——跨小时运行、可暂停恢复、强事务补偿的复杂流程。
仁菜：……那不能只靠模型工具循环。
桑多涅：要结合工作流引擎、消息系统或者图编排方案。
仁菜：那同类的 Java 方案怎么选呀。
桑多涅：还是看团队原有技术栈，不是比谁的组件名称更多。以 Spring 为中心的，重点比 Spring AI。
仁菜：用微软那套技术栈的呢。
桑多涅：评估 Semantic Kernel。Quarkus 项目优先看 Quarkus LangChain4j。
仁菜：那最后拿什么定呢。
桑多涅：做一个小型真实 PoC，不要只比功能清单。
仁菜：PoC 要验什么呢。
桑多涅：同一批问题，验回答质量、工具参数准确率、结构化输出成功率、延迟、Token 成本、监控完整度和故障恢复。
仁菜：……七样。
桑多涅：因为支持某项功能，和满足你自己的生产要求，中间还隔着业务数据和工程验证。
仁菜：……我今天的学费，正好撞在这句上。
桑多涅：说。
仁菜：我下午去后端组问了一句——我们那套订单系统是 Spring Boot 的。
桑多涅：多大。
仁菜：……十一万行，跑了八年。
桑多涅：那你原来的方案是什么。
仁菜：写一个 Python 服务，去调它暴露的 HTTP 接口。
桑多涅：那鉴权呢。
仁菜：……我在 Python 那边自己重写了三处判断。
桑多涅：……三处。
