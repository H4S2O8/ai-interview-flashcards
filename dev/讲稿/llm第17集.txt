llm第17集　什么是 CoT？为啥效果好？它有什么缺点或局限性？
============================================================

仁菜：欢迎回来，我是仁菜。榴莲酥……两个。
桑多涅：……我只吃一个。
仁菜：你真吃？！
桑多涅：我说了甜点你带，没说我挑。预算。
仁菜：百分之九——测试集我攒了三十二条了。
桑多涅：比昨天说的多两条。那今天讲昨天没展开的——CoT。
仁菜：这个我知道！Chain-of-Thought，让模型一步步思考，效果会更好。
桑多涅：「让模型一步步思考」是表面话——为什么一步步思考效果就好。
仁菜：呃……
桑多涅：模型有「想」吗。
仁菜：……它只是在生成 token。
桑多涅：再问你，CoT 一定有用吗——什么场景下会反而拖累效果。
仁菜：还有反效果？我以为 CoT 都是好的。
桑多涅：典型的「只看好处不看代价」——今天把两面都讲。先说没有 CoT 的时候，模型在干什么。
仁菜：直接给答案？
桑多涅：像什么——你打个比方。
仁菜：像……人没睡醒的时候凭直觉答题？看到题目，从记忆里拼出一个听起来合理的答案。
桑多涅：跳过了什么。
仁菜：跳过了中间的推理过程！
桑多涅：对简单问题没什么问题。但一旦涉及多步计算、逻辑推导或者因果链呢。
仁菜：就容易出错……因为它没有一步步检查自己的逻辑。
桑多涅：举个具体的——小明有五个苹果，给了小红两个，然后又买了三个，最后还剩几个。
仁菜：六个。
桑多涅：模型直接输出答案的话，可能怎么错。
仁菜：可能只做了一步运算？比如只算了减法，答三个。
桑多涅：那让它写出推理过程呢。
仁菜：「初始五个，给出两个后剩三个，再买三个后变成六个」——每一步都很容易验证！
桑多涅：所以 CoT 的本质是什么。
仁菜：让模型「推出来」，而不是「直接猜出来」。
桑多涅：但这里有一层你昨天已经碰到过的。
仁菜：昨天……哦！「让模型推理」和「把完整推理链展示给用户」不是一回事。
桑多涅：现代产品和 API 往往会怎么做。
仁菜：让模型内部完成推理，最终只给用户简洁答案、关键依据，或者可核查的步骤。
桑多涅：这样既保留推理收益，又避免输出冗长、不稳定的思考链。现在讲最核心的一个洞见。
仁菜：什么洞见？
桑多涅：模型是怎么生成的。
仁菜：一个 token 接一个 token……
桑多涅：每生成一个新 token 的时候，它能看到什么。
仁菜：前面所有已经生成的内容！
桑多涅：所以让它先生成推理步骤，等于给后面的答案生成提供了什么。
仁菜：……更多的工作记忆？
桑多涅：语言模型生成 token 的方式本身，就支持这种逐步推理。这一句是这道题的题眼。
仁菜：那 CoT 具体怎么实现？
桑多涅：两种形式——第一种，Few-shot CoT。
仁菜：在 Prompt 里给几个完整的推理示例？每个都包含问题、逐步推理过程和最终答案。
桑多涅：模型看到这种模式，会自动对新问题套用同样的推理格式。这种效果最稳定。
仁菜：适合对准确率要求高的场景。第二种呢？
桑多涅：Zero-shot CoT，更简单粗暴——在问题末尾加一句「请分步思考后再给结论」。
仁菜：就这一句？
桑多涅：这是研究里发现的一个有趣现象：仅仅这一类指令，就能激活模型的推理能力。
仁菜：不用写示例，Prompt 更简洁。那效果呢？
桑多涅：通常略逊于 Few-shot CoT，但很多场景下已经够好。现在说为什么有效，三个角度。
仁菜：第一个我刚说了——工作记忆？
桑多涅：换个说法：中间步骤充当了草稿纸。复杂的中间状态不用全部存在模型的隐状态里。
仁菜：显式写下来，减轻了推理负担——第二个角度？
桑多涅：逐步推理让每一步的错误都暴露出来。
仁菜：方便发现和纠正……而不是把错误藏在一个不透明的答案里。
桑多涅：第三个角度更底层——CoT 激活了模型在预训练时学到的推理模式。
仁菜：从哪儿学的？
桑多涅：大量推理型文本——数学解题、逻辑分析这些。
仁菜：所以 CoT 不是「教会」它推理，是「唤醒」它已经学过的推理模式。
桑多涅：……这个说法可以。还有一个升级版，Self-Consistency。
仁菜：这个我没听过。
桑多涅：对同一个问题，用较高的温度生成多条不同的推理路径，然后取最终答案里出现最多次的那个。
仁菜：多数投票？那这个直觉是什么。
桑多涅：你自己想——正确答案和错误答案，在多条路径上的表现有什么不同。
仁菜：正确的答案……可以通过多种不同的推理路径得到？
桑多涅：错误的呢。
仁菜：错误往往是随机产生的——不同路径不太可能收敛到同一个错误答案！
桑多涅：实验里能在 CoT 基础上再提升五到十五个百分点，数学推理类任务尤其明显。
仁菜：那我们全用这个——
桑多涅：……代价呢。
仁菜：要生成多条路径……调用次数变多？
桑多涅：通常五到十次——成本和延迟都跟着上去。
仁菜：五到十倍……那还是得挑场景用。
桑多涅：这就引到 CoT 本身的局限了。第一个你已经说了。
仁菜：token 消耗大？推理链会额外生成几百甚至上千个 token。
桑多涅：API 成本和响应时间都显著增加。第二个局限。
仁菜：呃……
桑多涅：对简单问题适得其反——你让模型对「一加一等于几」也展开推理，会怎样。
仁菜：浪费 token、降低速度……而且准确率一点没提升。
桑多涅：第三个局限最要命。
仁菜：比浪费钱还要命？
桑多涅：推理链本身也会出错。如果第二步推错了呢。
仁菜：第三步、第四步会基于错误的前提继续推……
桑多涅：最终答案大概率也是错的。所以要记住一句话——CoT 能减少跳跃性错误，但不能消除推理错误。
仁菜：这两个的区别是……跳跃性错误是「不推就猜」，推理错误是「推了但推歪了」？
桑多涅：后者 CoT 治不了，甚至会放大——因为错误会沿着链条传导。
仁菜：还有第四个局限吗？
桑多涅：对纯粹依赖记忆的任务没帮助——比如问「二零二零年奥运会在哪里举办」。
仁菜：这种问题根本不需要推理，让它分步分析纯属浪费。
桑多涅：所以 CoT 是为什么设计的工具。
仁菜：为「需要多步推理」的问题——数学、逻辑题、代码调试。
桑多涅：不需要推理的呢。
仁菜：简单问答、分类、信息提取，用普通 Prompt 就好。
桑多涅：那回到你们的场景——客服问答，该不该默认开 CoT。
仁菜：大部分不该……但涉及退款金额计算、多条政策叠加的，应该开。
桑多涅：所以不是「开不开」，是什么。
仁菜：是按问题类型分流！先判断这道题需不需要推理，再决定用哪套 Prompt。
桑多涅：……这个结论比背四条局限值钱。
仁菜：那明天组会我怎么讲？
桑多涅：先讲为什么有效，落在那个题眼上——模型逐 token 生成、能看到前文，所以中间步骤是它的工作记忆。
仁菜：然后是两种形式：Few-shot CoT 稳但要写示例，Zero-shot CoT 一句话就能激活。
桑多涅：然后是 Self-Consistency 和它的代价。最后是四个局限。
仁菜：面试官要是只问「CoT 是什么」呢？
桑多涅：那你主动把局限讲出来——只讲好处的人，一听就是没在生产上用过。
仁菜：学费——我按问题类型给测试集打了标：三十二条里，只有七条真正需要多步推理。
桑多涅：……这算数据。七比三十二。那你的结论。
仁菜：默认不开 CoT，只对那七类开。要是全开，我们百分之七十八的请求都在白烧 token。
桑多涅：明天讲一个你上一季啃过的东西——幻觉。但角度不一样。
仁菜：上一季讲的是检索侧怎么压……
桑多涅：明天讲模型侧为什么会——青团，入春了。
仁菜：啊，青团！我是仁菜，我们下集见。
