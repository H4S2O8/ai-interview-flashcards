tools第06集　MCP 和 Function Calling 有什么区别？有没有实际跑过 MCP？
============================================================

仁菜：欢迎回来。我是仁菜。熔岩巧克力，现在切开 —— 你看这流心，完美的，别皱眉。
桑多涅：……嗯，火候过关。六天。上两集把 MCP 的皮和零件都拆了，今天把两张图合成一张动态图。先答：MCP 和 Function Calling 什么关系？
仁菜：这我还真想好了：MCP 是 Function Calling 的升级版嘛。MCP 都出来这么久了，以后工具调用全走 MCP，Function Calling 迟早淘汰 ——
桑多涅：淘汰？
仁菜：对啊，新东西出来，旧的退场，很合理吧？
桑多涅：那我问你，MCP 的底层靠什么驱动的？
仁菜：靠什么……Client 连 Server、转发调用，这不就是 MCP 自己的活儿吗？
桑多涅：模型那边呢？模型靠什么表达「我要调工具」？
仁菜：靠输出 tool_calls……啊？？那就是 Function Calling 啊。
桑多涅：对。MCP 底层就是 Function Calling 在驱动。你要淘汰它，等于房子盖到三楼，嫌地基旧，把地基拆了。
仁菜：……那、那我改口，MCP 是给它包了层壳？功能上没区别，就是写法不一样？
桑多涅：如果只是写法不一样，Anthropic 为什么要专门设计一个协议？写法之争用不着协议。Function Calling 管的是单次调用的格式，MCP 管的是一堆工具怎么标准化管理、跨项目复用、自动发现。抽象层次完全不同。
仁菜：层次……我总撞在这堵墙上。给我一个能记住的坐标系吧。
桑多涅：有一个现成的。HTTP 协议出来之后，网络上传数据这件事就已经会了，那后来为什么还要有 REST 这套规范？
仁菜：HTTP 管一次请求怎么发 —— 用什么方法、怎么编码；REST 管的是资源怎么命名、端点怎么设计、一堆服务之间怎么遵守同一套约定。传，和组织管理，两回事。
桑多涅：照抄过来就行。Function Calling 就是 HTTP 请求格式 —— 一次调用长什么样；MCP 就是 REST 那套规范加服务注册发现 —— 一堆工具怎么组织、怎么被找到、怎么跨项目复用。格式，和生态约定，少谁这套机制都转不起来。
仁菜：那 Function Calling 自己过日子是什么样？你说它管单次调用 ——
桑多涅：全是手工活。工具定义的 schema 你手写，模型要调了你手写调用逻辑，结果回来了你手动塞回去。它没有任何工具管理、发现、复用的概念 —— 一次一清，下次重来。
仁菜：一次一清也没什么吧，复制粘贴的事？
桑多涅：那我给你算笔账。你在 A 项目里定义了十个工具的 schema 和对接逻辑，现在 B 项目也要用，怎么办？
仁菜：复制……再适配一遍。
桑多涅：A 项目用的 Claude 的接口，B 项目换成 GPT-4，两家的 Function Calling 格式还不太一样，各自再维护一套适配。还没完 —— GitHub 的接口哪个字段改了，你得去每个用到它的项目里同步改，五个应用八个工具，四十份对接代码，漏改一处，那个应用凌晨三点报警，报警的人是你。
仁菜：四十份……这不是写代码，这是养四十只宠物。
桑多涅：所以 MCP 的思路才立得住：把工具做成独立的标准化服务。GitHub 官方写一个 MCP Server，能力封装好、标准接口对外，谁的 Client 连上来就自动发现、直接用。写一次，到处用。
仁菜：这段我懂，上两集都拆过零件了。但有个环节我从来没想明白：Server 里的工具，是怎么「进到」模型脑子里的？模型上季就学会了 Function Calling，它又不知道 MCP 的存在。
桑多涅：问到今天最值钱的一步了。MCP Client 连上 Server，先调一个 list_tools，把 Server 里所有工具定义拉下来；然后做翻译 —— 把这些定义转换成模型原生的 Function Calling 格式，塞进请求里。模型一看，跟平时一样，按它学过的方式输出 tool_calls；Client 再把这个请求路由到对应的 Server 执行，结果以 tool 消息喂回对话。
仁菜：所以模型全程无感？！它以为自己就在做普通的 Function Calling，根本不知道背后有一堆 Server 在跑？
桑多涅：它不知道。工具的自动发现、schema 的格式转换、调用请求的路由、结果的返回，全部魔法都发生在宿主程序那一层，模型眼前只有一张熟悉的表格。
仁菜：等等 —— 这个推论有点狠：要是模型本身不支持 Function Calling，MCP 是不是整个就废了？翻译层没了。
桑多涅：废了，一步都走不通。所以别再说谁淘汰谁 —— MCP 站在 Function Calling 肩膀上，脚底下那只肩膀一抽，它先摔死。
仁菜：这图我记住了。那……你到底跑过没有？你说得跟真用过似的。
桑多涅：配过。Claude Desktop 里接文件系统和 GitHub 的 Server，配置文件加几行：用什么命令启动 Server、允许它碰哪个目录，重启，工具自动出现。我让它读文档里的一个文件，它自己调工具完成的，全程我没写一行对接代码。后来嫌不够，自己写过一个：声明有哪些工具、每个工具的执行逻辑、用 stdio 跑起来，三十行以内，通信那些全由 SDK 包了。
仁菜：……那面试官问「有没有实际跑过」，我都不知道怎么答。我总不能现编吧？
桑多涅：不许编。没跑过就说没跑过，然后讲你怎么理解它的设计 —— 面试官问这句不是考背诵，是看你是背的概念还是摸过的东西。编的，追问一个细节就穿，穿了比没跑过难看十倍。
仁菜：那怎么办，补作业？
桑多涅：三十行的事，今晚就写一个。写完你面试说「我自己动手接过」，底气都不一样。
仁菜：行，今晚写！那最后给我个选型的边界吧，什么时候用哪个？
桑多涅：临时给自己的应用接一两个工具，Function Calling 够了，简单直接，犯不着为一个工具引入协议、进程、配置一整套。工具多了、要跨项目复用、或者社区里现成 Server 就有 —— GitHub、数据库、浏览器自动化 —— 上 MCP，接新工具就是改几行配置。做 Agent 系统，工具来源杂、数量多，更该上，新增工具不用改主程序。
仁菜：那干脆所有项目都直接上 MCP 不就完了，一步到位 ——
桑多涅：又来了。上集刚说过分层，这集就「全上」。为一个临时工具引一整套协议，进程管理、配置维护、生命周期全是成本，杀鸡用牛刀，鸡没死厨房先塌了。
仁菜：……有依赖看场景，没依赖才并行 —— 呸，串词了，意思懂就行：看场景选型，不无脑上。
桑多涅：你自己找补的，记住就好。
仁菜：我过一遍：FC 是调用语言，管一次调用长什么样；MCP 是生态协议，管工具怎么组织、发现、复用，好比 HTTP 和 REST 的关系；痛点是四十份手工对接，MCP 让工具写一次到处用；关键机制 —— Client 拉定义、翻译成 FC 格式、模型无感输出 tool_calls、路由执行；模型不支持 FC，MCP 直接废。选型：一两个工具用 FC，工具多、跨项目、做 Agent 上 MCP。
桑多涅：……链路说全了。就选型那条，你开头还想「全上」呢。
仁菜：所以印象才深嘛！下集预告：两个都讲透了，该回答那个终极问题 —— 到底什么场景用 Function Calling，什么场景用 MCP。甜点，水果挞，我选的。我是仁菜，我们下集见。
桑多涅：水果挞……花哨。明天看我切不切你。
