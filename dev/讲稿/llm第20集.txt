llm第20集　大模型部署有哪些主流方案？vLLM、TGI、llama.cpp、SGLang 实际项目里怎么选？
============================================================

仁菜：欢迎回来，我是仁菜。杨枝甘露——甜的，压压昨天的苦。
桑多涅：预算。
仁菜：还剩百分之九十一没花——但导师今天说，下周要出部署方案了。
桑多涅：那今天这道题是你真要用的——先说你现在知道什么。
仁菜：vLLM 用来部署大模型推理，速度快；llama.cpp 是 CPU 推理；TGI 和 SGLang 我没用过。
桑多涅：「速度快」是表面话——vLLM 凭什么比直接用 transformers 库快。
仁菜：呃……它优化过？
桑多涅：PagedAttention 是什么。为什么这个名字叫 Paged。
仁菜：分页管理 KV Cache？类似操作系统的虚拟内存？
桑多涅：方向对——具体怎么 Paged，你能讲清楚吗。
仁菜：……讲不清楚。
桑多涅：再问一个——SGLang 的 RadixAttention 和 vLLM 的 PagedAttention 是什么关系。
仁菜：RadixAttention 我完全不熟。
桑多涅：那今天从头。先问一个更基础的——直接用 transformers 库跑模型，会有什么问题。
仁菜：应该能跑起来吧？
桑多涅：能跑起来，但效率很糟——三个痛点，第一个跟你最近算的账有关。
仁菜：显存？
桑多涅：每来一个请求，朴素实现会预分配「最大可能长度」的 KV Cache 显存。比如四千零九十六个 token。
仁菜：可实际上大多数请求哪用得了那么多……
桑多涅：两百到五百个 token 就完了。剩下三千多个 token 的显存呢。
仁菜：空着浪费！那浪费多少？
桑多涅：一台八十 GB 的 H100，理论能跑一百个并发，实际只能跑三十个。
仁菜：浪费了六七成……这就是第一个痛点，显存碎片。第二个呢？
桑多涅：批量推理调度低效——朴素的做法叫 static batching，凑齐一批请求一起跑、一起结束。
仁菜：那要是有的请求五十个 token 就完了，有的要一千个——
桑多涅：短的等长的——GPU 大量时间在「跑了一半在等」。
仁菜：吞吐率上不去——第三个痛点是重复计算？
桑多涅：每个用户都用同一段 System Prompt 的时候。
仁菜：这个我太熟了！第十四集——每次都重新算那一千个 token 的 KV Cache。
桑多涅：所以部署框架就是为了解决这三个痛点。三大优化方向，你总结。
仁菜：内存高效对显存碎片，批量调度对吞吐率，缓存复用对重复计算。
桑多涅：每个主流框架在这三个方向上都有自己的创新。先说 vLLM。
仁菜：它的 PagedAttention 到底做了什么？
桑多涅：灵感来自操作系统的虚拟内存——操作系统怎么管理内存的。
仁菜：呃……给每个进程分一块内存？
桑多涅：如果是预分配大块连续物理内存，会有什么问题。
仁菜：大量碎片！就像刚才那个「预分配四千零九十六实际只用两百」。
桑多涅：所以操作系统怎么做的。
仁菜：把物理内存切成固定大小的页？然后……进程拿到的是逻辑地址？
桑多涅：通过页表映射到真实的物理页——这样物理内存可以充分利用。
仁菜：那 PagedAttention 就是把这个搬到 KV Cache 上——把显存切成固定大小的块！
桑多涅：典型是十六个 token 的 KV 一块。每个请求拿到的是逻辑 KV 序列，由一张表映射到物理块。
仁菜：那一个请求实际用了两百个 token，就只占十三块左右？
桑多涅：用完即释放。没有「预分配四千零九十六但只用两百」的浪费。效果呢。
仁菜：显存利用率能提多少？
桑多涅：从三到四成拉到九成以上——同样硬件能跑两到四倍的并发。
仁菜：两到四倍……那我们那点卡，等于凭空多出来一倍多。
桑多涅：vLLM 还有第二个杀手锏，针对第二个痛点。
仁菜：批量调度？
桑多涅：Continuous Batching，连续批处理。朴素做法是凑齐一批一起跑一起结束。
仁菜：那连续批处理是——请求可以随时加入和退出？
桑多涅：每个 token 步骤动态组 batch。A 生成完了退出，立刻有新请求 D 加入。
仁菜：GPU 就不用「跑了一半在等」了！
桑多涅：这两个加起来，就是 vLLM 一出来就把行业标准提了一个量级的原因。现在说 SGLang。
仁菜：它解决哪个痛点？
桑多涅：第三个——它的核心创新叫 RadixAttention。
仁菜：Radix……前缀树？
桑多涅：把多个请求的共享前缀组织成树结构，相同前缀只存一份 KV Cache。
仁菜：共享前缀……比如 System Prompt？
桑多涅：还有 Few-shot 示例、对话历史。什么场景前缀重复率最高。
仁菜：Agent！多轮对话！还有批量跑 Prompt 的时候——
桑多涅：所以在这些场景下，它比 vLLM 显存更省、首 token 延迟更低。
仁菜：那这和 Prompt Caching 是一回事吗？
桑多涅：……问得好。你觉得呢。
仁菜：第十四集说 Prompt Caching 是把 KV Cache 从「单次推理内」扩展到「跨请求」……
桑多涅：RadixAttention 是它在框架层的一种实现方式——用前缀树来组织，多个请求天然共享。
仁菜：所以是同一个思路，不同的实现层次。
桑多涅：第三个框架，TGI，HuggingFace 出品。它的优点是什么。
仁菜：和 HF 生态深度集成？
桑多涅：开箱即用、支持 Hub 上的各种模型、还有企业级 API 接口——鉴权、metrics、健康检查。
仁菜：那它性能呢？我们要不要考虑——
桑多涅：这里得说准——它近两年的增长势头不如 vLLM 和 SGLang。
仁菜：那还有人选它吗？
桑多涅：选它更多是看中 HF 生态和既有系统集成，不是追求极致性能。这两个理由不能混着说。
仁菜：第四个是 llama.cpp？
桑多涅：CPU 和边缘设备部署的事实标准。用 C++ 重写整个推理栈，配合 GGUF 量化格式。
仁菜：GGUF——第十五集讲过，是格式不是算法。那它能跑在哪儿？
桑多涅：七十亿的模型可以在笔记本上跑、在树莓派上跑、在手机上跑。
仁菜：没有 GPU 也能跑……那是个人开发者的首选了。
桑多涅：还有第五个，TensorRT-LLM，NVIDIA 官方的。追求极致性能、愿意自己定制的场景用。
仁菜：那现在回到选型——我该怎么选？
桑多涅：你自己答——生产环境要高吞吐的 LLM API，选什么。
仁菜：vLLM。
桑多涅：Agent、多轮对话、Few-shot 重的场景。
仁菜：SGLang 更省，因为前缀重复率高。
桑多涅：要拥抱 HF 生态、企业级接口的。
仁菜：TGI。本地、Mac、边缘、没有 GPU 的——llama.cpp。
桑多涅：那你们呢。
仁菜：我们是客服，System Prompt 三千 token，所有请求都用同一个前缀……
桑多涅：说下去。
仁菜：前缀重复率高得离谱。而且我们不是 Agent，但这个特征和 Agent 是一样的——
桑多涅：所以。
仁菜：SGLang——而且这个理由不是「它比较新」，是「我们的前缀重复率高，RadixAttention 正好吃这一口」。
桑多涅：……这个答案我认。它是从你的负载特征来的。
仁菜：可是我还得验一下。
桑多涅：怎么验。
仁菜：拿我们真实的请求分布跑一遍，量首 token 延迟和显存占用，vLLM 和 SGLang 各一遍。
桑多涅：……第八集那个五格清单，你现在自己会填了。
仁菜：那明天组会我怎么讲这道题？
桑多涅：先讲三个痛点——显存碎片、调度低效、重复计算。这是所有框架存在的理由。
仁菜：然后是每家解决哪一个：vLLM 的 PagedAttention 对显存碎片、Continuous Batching 对调度；SGLang 的 RadixAttention 对重复计算。
桑多涅：TGI 和 llama.cpp 的定位说清楚，别当成性能竞品。
仁菜：最后落到「按负载特征选」，不是「按流行度选」。
桑多涅：还有一句 —— 说 vLLM 快，要能说出快多少、什么并发下、显存多少。
仁菜：填不上就是没部署过。
桑多涅：这就是这道题真正在考的。学费。
仁菜：有！我把我们的请求长度分布量了：中位数两百三十七个 token，九十分位六百一十四，但预分配是四千零九十六。
桑多涅：……这算数据。那你算出浪费多少了吗。
仁菜：按中位数算，九成四的预分配显存是空着的。
桑多涅：带上分位数和预分配值一起报。明天讲怎么量效果 —— 你今天报的这些数，明天要变成一套指标。桂花糖藕。
仁菜：终于要讲评测了！我是仁菜，我们下集见。
