rag第05集　怎么规避语义被切割掉的问题？
============================================================

仁菜：欢迎回来，我是仁菜。条头糕——……昨晚我没写脚本。
桑多涅：为什么。
仁菜：因为你说别急着跑全量嘛。我就先手动试了几段——然后就撞上昨天那个问题了。
桑多涅：……举个具体的。
仁菜：我们条款里有一句：企业用户享有优先客服通道，响应时间不超过两小时，并可申请专属技术顾问服务。边界正好切在中间。
桑多涅：切开之后呢。
仁菜：「企业用户享有优先客服通道」在前一块——「并可申请专属技术顾问服务」在后一块。
桑多涅：那你搜「企业用户能申请技术顾问吗」，会怎样。
仁菜：应该能搜到后一块吧？里面有「专属技术顾问」。
桑多涅：你试了吗？
仁菜：……试了。两块都没被召回。
桑多涅：这就是语义截断的核心——不是信息丢了，是信息被拆散之后，每一半都不够强，检索时全军覆没。
仁菜：那加 overlap 不就好了？前后重叠一百个 token。
桑多涅：overlap 只是兜底——它能保证跨边界的文字不丢失，但解决不了一个完整语义被拆散的问题。
仁菜：诶？这两个不是一回事吗。
桑多涅：不是。你那句话即使有重叠，两块单独看相关度还是不高——文字在，语义散了。
仁菜：……那我把 chunk 设大一点？每块装更多内容就不会断了。
桑多涅：块越大语义越杂，检索精度越差——你这是用一个问题去换另一个问题。
仁菜：……又被我绕回去了。
桑多涅：今天讲六种方案，从兜底到最狠的。第一种呢，你已经会了。
仁菜：重叠切割呗。重叠量设多少？
桑多涅：通常是块大小的百分之十到二十——比如块大小八百，重叠一百五。
仁菜：那为什么不直接设百分之四十？多重叠一点不是更保险吗。
桑多涅：这是实践摸出来的平衡点。太小了，比如百分之五——重叠区覆盖不了完整的跨边界语义，保护很弱。
仁菜：太大呢？
桑多涅：重复内容太多，存储和检索成本上去了，而且大量重复还会干扰模型的阅读和理解。
仁菜：所以它是每个系统都该开、但开了也别指望它解决问题的那种。
桑多涅：准确。第二种，在切的时候就聪明一点。
仁菜：语义边界切割——找文本里天然的断点再切。为什么句子边界最要紧？
桑多涅：句子是语言表达意思的最小完整单位——有主语谓语宾语，能独立表达一个意思。从中间截断，前后两截单独看都是残缺的。
仁菜：向量化之后语义也是扭曲的。
桑多涅：工程上用 NLP 工具识别句子结束位置——spacy 或者 nltk 都行。然后以句子为单位往块里填。
仁菜：填满了就封存，开新的一块，绝不在句子中间截断。
桑多涅：段落分明的文档，还可以优先在段落边界切，效果更好。前两种都是在「怎么切」上做文章。第三种开始，思路变了。
仁菜：变成什么？
桑多涅：切归切，检索的时候再把上下文补回来。
仁菜：……这个思路我喜欢！
桑多涅：句子窗口检索。存储时把文档切成单个句子，每句单独做向量，用于精准检索。
仁菜：那命中之后呢？只返回那一句？
桑多涅：不——把这句前后各若干句一起返回，形成一个上下文窗口，交给模型读。
仁菜：哦——就像我在图书馆用关键词找到某本书里的一句话，但实际读的是这句话所在的整段，不是只拿走那一行。
桑多涅：两全其美：检索粒度细，定位准；给模型的却是完整上下文。缺点呢。
仁菜：每个句子都要单独向量化……库里的记录数等于文档的句子总数？
桑多涅：存储量会很大。你那四万份，自己算。第四种。
仁菜：父子切割！这个昨天讲过——小块检索，大块生成。
桑多涅：那它和句子窗口的区别在哪。
仁菜：呃……感觉挺像的。
桑多涅：句子窗口是检索命中后动态扩展上下文——父子切割是提前把父子关系存好。
仁菜：所以父子切割更可控，父块多大是我定的；句子窗口实现更简单，不用维护父子 ID 关系。
桑多涅：嗯。第五种，质量最高，成本也最高。
仁菜：比父子切割还高？
桑多涅：命题化切割——不按文本位置切，而是用大模型把文档分解成一条条独立的命题。
仁菜：命题是什么意思？
桑多涅：一个完整、自包含的陈述句——包含表达这个事实所需的全部上下文，单独拿出来就能看懂，而且只包含一个核心事实。
仁菜：那我那句话会被拆成什么？
桑多涅：三条——企业用户享有优先客服通道。企业用户的客服响应时间不超过两小时。企业用户可以申请专属技术顾问服务。
仁菜：……每一条都自带主语！单独拿出来都能看懂，不需要任何上下文。
桑多涅：语义密度极高，检索精度非常好。代价。
仁菜：要额外调大模型来生成命题——成本高。
桑多涅：适合对质量要求极高的场景。第六种，思路和前面五种都不一样。
仁菜：还能怎么不一样？
桑多涅：不改怎么切，也不管检索后怎么扩展。它在向量化之前，就把缺失的上下文补进去。
仁菜：……啊？
桑多涅：Anthropic 二零二四年提出的，叫 Contextual Retrieval。先说它要解决的根本问题：一个 chunk 被单独拿出来之后，就失去了语境。
仁菜：这话怎么讲。
桑多涅：举个例子。有段文字是「此条款自二零二四年一月一日起生效」。单独向量化，向量里有什么。
仁菜：有……日期？生效？
桑多涅：没有「这是企业版客服条款」这个信息。Embedding 模型只看得到这段文字本身，不知道它来自哪篇文档、讲的是什么主题。
仁菜：可是向量不是能捕捉语义吗？
桑多涅：它只能捕捉它看到的文字里的语义——看不到的背景，自然编码不进去。向量里没有主题信息，就是孤立 chunk 召回质量低的根本原因。
仁菜：那 Contextual Retrieval 怎么补？
桑多涅：两步。第一步生成 Context——让大模型看着整篇原始文档，为每个切出来的块生成一两句话的背景说明，说清楚它在整篇文档里处于什么位置、讲的是什么。
仁菜：第二步是把这段说明拼到块前面？
桑多涅：拼上去之后，把「背景加原块」整体拿去做 Embedding 和 BM25 索引。
仁菜：那刚才那个例子，生成的背景会是什么样？
桑多涅：大概是「本节介绍企业版用户的客服服务条款」这类。拼起来向量化，这个块的向量里就有了企业用户、客服条款、生效日期这些关键语义。
仁菜：被正确召回的概率就大幅提升了……可是等一下！
桑多涅：说。
仁菜：每个块都要调一次大模型？我四万份文档切出一百多万块，这得多少钱啊。
桑多涅：问得对。这是它最大的顾虑。但有个特性能把成本压下去百分之八十到九十。
仁菜：什么特性？
桑多涅：Prompt Caching——每次调用时，完整文档在所有块的请求里是相同的前缀。开了缓存，第一次调用把文档内容缓存住，后续同一篇文档的所有块请求都复用这份缓存，只有块的部分要重新算。
仁菜：那省下来多少？
桑多涅：算笔账。一篇有一百个块的文档，传统做法要把整篇文档的 token 重复处理一百次。开了缓存，第一次写入按正常价的一点二五倍计费，有百分之二十五的写入溢价；后面九十九次命中缓存的部分只按正常价的百分之十计费。
仁菜：综合下来文档部分的成本降到原来的百分之十到二十。
桑多涅：按 Anthropic 官方参考数据，八千 token 的文档配八百 token 的块，处理一百万文档 token 的总成本大约一美元出头。
仁菜：一美元？！那我刚才白紧张了。
桑多涅：工程上只要在调用时把文档内容标记为可缓存前缀，框架会自动复用。效果数据你也记一下。
仁菜：有实测？
桑多涅：Contextual Retrieval 结合 BM25 混合检索，能把检索失败率降低约百分之四十九——检索失败率指的是前二十条召回里没命中目标块的比例。
仁菜：降一半……这是目前业界实测效果最显著的方案之一了吧。
桑多涅：是。所以今天六种，你实际怎么组合。
仁菜：重叠切割一定开，兜底；有结构的按语义边界切；对召回质量要求高的，上父子切割或者句子窗口；质量要求极高、预算又够——就上 Contextual Retrieval。
桑多涅：够了。学费。
仁菜：今天数了一下：我们那批条款文档，平均每篇有十一处这种跨句拆分的高风险位置。我标出来了。
桑多涅：……这算数据。十一处，条款类文档，人工标注。带上这三个。
仁菜：知道啦。那明天呢？地基算是打完了？
桑多涅：打完了。明天开始选型——你得先搞清楚 Embedding 到底是什么，怎么评估。双酿团。
仁菜：终于到我心心念念的选型了！我是仁菜，我们下集见。
桑多涅：……你那个「心心念念」，明天我会记着的。
