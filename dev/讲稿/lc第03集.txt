langchain第03集　LangChain 的底层架构与实现原理是什么？
============================================================

仁菜：欢迎回来，我是仁菜。黑芝麻糊 —— 今天我请，因为昨天你那句话戳到我了。
桑多涅：哪句。
仁菜：包到第几层开始改不动的。……进度还剩五周，那四百二十行我还没删。
桑多涅：那今天看完再决定。底层架构，你先说。
仁菜：LangChain 就是把 Prompt、模型和解析器串成一条 Chain。
桑多涅：……你今天连铺垫都不铺了。
仁菜：嘿嘿。省时间嘛，你直接打。
桑多涅：那我按面试官的问法打。不同厂商的模型如何统一？工具结果怎样回到模型？Agent 的状态和循环又由谁管理？
仁菜：……底层应该就是一个 while 循环吧？模型要调用工具就执行，不调用就退出。这个我是真这么写的。
桑多涅：表面行为是像。但生产级 Agent 还需要路由、持久化、中断恢复和人工介入，而且现在 create_agent 底层运行在 LangGraph 上。
仁菜：那我记住 create_agent 底层是 LangGraph，应该就算理解架构了吧？
桑多涅：还不够。Message、Tool、State、Context、Store、Middleware 分别负责什么，它们又怎样协作 —— 这才是架构题真正要讲的。这道题的判据只有一条：你能不能从一次 Agent 请求出发，讲清各层怎么协作。
仁菜：六个东西……那从头来。LangChain 到底解决了什么？
桑多涅：先问你 —— 直接调用一家模型厂商的 SDK，难吗。
仁菜：不难啊，文档看半小时就能跑通。
桑多涅：那问题什么时候出现。
仁菜：……应用变复杂之后？
桑多涅：不同厂商的消息格式、工具调用结构、流式响应，各不相同。业务还要接 Prompt、工具、状态、重试、追踪。等你要换模型的时候，大量厂商专属字段可能已经散落在你的业务代码里了。
仁菜：……我们上个月就是这样。切模型那次我改了十七个文件，还漏了两个，测试的时候才发现。
桑多涅：所以 LangChain 的核心思路是在这些差异之上定义稳定接口 —— 厂商集成负责适配，应用只依赖公共协议。
仁菜：那它分几层呀？
桑多涅：抓住四层。最底下是 langchain-core，定义 Message、Model、Tool、Runnable 这些标准协议。往上是各家厂商的独立集成包，负责把自己的请求响应适配到这些协议。
仁菜：第三层是执行层吧？Runnable 统一同步、异步、批处理、流式。
桑多涅：第四层是应用层：步骤固定的用 LCEL 组合，要模型自主选工具的用 create_agent。可观测性贯穿各层，用运行事件和 Trace 记录调用、耗时和异常。
仁菜：所以这四层就是严格的调用顺序咯？
桑多涅：……不是。这里要说准 —— 这张分层图表达的是职责边界，不是严格的单向调用顺序。比如模型和编译后的 Agent 都遵循 Runnable 的调用方式，但它们承担的架构角色完全不同。
仁菜：……所以都是 Runnable 不代表在同一层。分层图最容易被读成调用链。
桑多涅：现在讲协议 —— 一条数据怎么从用户走到模型，再进入业务系统。第一个统一是传什么：HumanMessage 表示用户输入，AIMessage 表示模型输出，ToolMessage 表示工具执行结果。不同厂商原本各有一套格式，适配成统一 Message 之后，上层就不用跟着每家 SDK 反复改动。
仁菜：那我那十七个文件，下次只要改集成包那一处？
桑多涅：对。但只有消息还不能完成业务动作，所以 Tool 接住下一棒。这里有个边界最容易搞错 —— 模型看到的是什么。
仁菜：工具名称、描述、参数 Schema。
桑多涅：它能做什么。
仁菜：它只能提出想调用哪个工具、参数是什么。真正执行 Python 函数或者外部服务的……是应用程序！不是模型。
桑多涅：所以权限校验和副作用必须留在应用这边。模型只是提议，不是执行。这条边界画不清，做出来的东西就有安全问题。第三个统一是怎么执行。
仁菜：Runnable。昨天讲过，invoke、异步、批处理、流式。那三者连起来我总结一下 —— Message 统一数据表达，Tool 划清模型与业务动作的边界，Runnable 统一执行方式。
桑多涅：所以 LangChain 才不只是替换模型 SDK 的薄封装。现在讲 Agent loop。
仁菜：这个就是那个 while 循环吧？
桑多涅：核心不是一次模型调用，是模型和工具之间可能重复多轮的执行循环。你把一轮拆开说。
仁菜：模型读取消息，生成 AIMessage。如果里面包含 tool_calls，运行时就执行对应工具，把结果包装成 ToolMessage 写回状态。然后模型再次读取工具结果，继续判断，直到生成最终回答。
桑多涅：这里有个字段特别重要 —— tool_call_id。为什么。
仁菜：呃……做标识用的？
桑多涅：模型一轮可能请求多个工具。
仁菜：哦——！那结果回来的时候，得知道每条结果属于哪一次调用！
桑多涅：没有这个 ID，多工具并发就对不上号。面试很爱追这个细节。
仁菜：那 create_agent 返回的是什么呀？
桑多涅：不是普通函数，是编译后的 LangGraph 图。
仁菜：编译……所以它能在每一步保存状态、输出进度、决定下一条执行边？
桑多涅：这就是它和你那个 while 循环的根本差别。
仁菜：……我的循环跑到一半断了，只能从头再来。
桑多涅：现在说数据放哪儿。Agent 里的数据，能不能全塞进消息或者 Prompt。
仁菜：不能吧？会很长。
桑多涅：不只是长。你想想，用户身份要不要让模型生成。
仁菜：……不行！那不就能伪造了吗。
桑多涅：数据库连接呢，能不能写进对话上下文。
仁菜：更不行，那是泄露。
桑多涅：所以运行时会区分几类数据：State 保存会变化的消息与业务状态，Runtime 提供可信上下文和长期 Store。工具通过 Runtime 读取这些，同时只把真正需要模型填写的参数，暴露在工具 Schema 里。
仁菜：哦——！所以模型该知道的和工具需要的，是两回事。
桑多涅：这条划分不做，你的用户身份就是模型编出来的。最后一层，Middleware。
仁菜：中间件？做什么用的呀。
桑多涅：真实应用要处理动态提示词、模型切换、工具筛选、重试和人工审批。
仁菜：这些我全塞在 Prompt 和 Tool 里了……然后代码就纠缠在一起了，改一个地方要看三个文件。
桑多涅：Middleware 提供的是模型和工具调用前后的扩展点。请求进模型前能做什么。
仁菜：根据用户身份生成系统提示词？还有历史消息太长的时候先做摘要。
桑多涅：模型决定调用工具之后呢。
仁菜：先检查权限！敏感动作还可以暂停等审批。真正执行的时候遇到临时网络故障，就在这一层做有上限的重试，结果返回之后再补格式或安全校验。
桑多涅：所以一次请求从进入模型到离开 Agent，各个阶段都有清楚的扩展位置。但有一句要说准 —— Middleware 不是另一套运行时。
仁菜：那它是什么？
桑多涅：它运行在 create_agent 编译出的那张 LangGraph 内部，对执行行为做组合式扩展。你在面试里说它是另一套运行时，等于承认你没看过它跑在哪儿。
仁菜：……记住了。那整个架构一句话怎么说？
桑多涅：用标准协议统一组件，用 create_agent 提供高层 Agent 入口，再由 LangGraph 承担有状态的执行运行时。这一句背下来。
仁菜：……那明天答辩，我就从一次请求出发走完这四层。中间三条边界一条都不能漏 —— 模型只提议、应用才执行；可信数据走 Runtime 不走消息；Middleware 跑在图内部。
桑多涅：还有 tool_call_id。那个细节最像做过的人。
仁菜：……
桑多涅：怎么。
仁菜：我那四百二十行里，没有 tool_call_id。我一直是单工具串行调的，所以从来没撞上过这个问题。
桑多涅：那你的东西在什么时候会崩。
仁菜：……模型一轮请求两个工具的时候。
桑多涅：学费。
仁菜：这就是学费。我今天翻了日志 —— 上周线上有十一次一轮请求多个工具，我的循环把后面那个直接丢了，没报错，没告警，什么都没有。
桑多涅：……这算数据。十一次，静默丢弃。带上时间范围一起报。
仁菜：所以我那四百二十行不是能用但不够优雅，是有一类情况根本就不对。
桑多涅：明天讲用它构建 Agent 的核心步骤。你会看到你漏的不止这一处。杏仁茶。
仁菜：……还有？
桑多涅：先去翻日志。
仁菜：……我今晚把日志再翻一遍。我是仁菜，我们下集见。
