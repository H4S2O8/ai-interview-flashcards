llm第19集　MoE 混合专家模型是什么？DeepSeek V3、Qwen 为什么用 MoE？
============================================================

仁菜：欢迎回来，我是仁菜。龟苓膏——真苦。
桑多涅：那就对了。预算。
仁菜：百分之九——今天不烧钱，今天烧脑子。
桑多涅：那开始——MoE 是什么。
仁菜：MoE 就是混合专家嘛——把多个小模型合在一起，每次用一个，效果好。
桑多涅：「合在一起」是怎么合的。
仁菜：呃……
桑多涅：「每次用一个」，具体是哪个组件决定的。
仁菜：应该有个 Router 来选？
桑多涅：这个我接受。再问你——MoE 是二零一七年 Google 就提出的，为什么二零二四年才在 LLM 领域火起来。
仁菜：因为 DeepSeek？
桑多涅：你说的是「火起来」，没说「为什么火起来」。MoE 解决了什么 Dense 模型解决不了的问题。
仁菜：……我没仔细想过。
桑多涅：那先看 Dense 的瓶颈——标准 Transformer，每个 token 推理时要走多少参数。
仁菜：全部？
桑多涅：一个一千七百五十亿的模型，每生成一个 token，就要让这一千七百五十亿个参数全部参与计算。
仁菜：那这里面的权衡就出来了……想提升能力得加参数，但参数加倍，推理成本也加倍。
桑多涅：具体到硬件上——一台八卡的 H100 服务器，能跑动七百亿的 Dense 模型。
仁菜：一千七百五十亿呢？
桑多涅：跑不动——所以 MoE 的核心创新是什么。
仁菜：呃……让参数变少？
桑多涅：不。是打破「知识量」和「推理成本」的绑定。
仁菜：打破绑定……怎么打破？
桑多涅：模型有 N 个专家，每个专家是一份独立的 FFN。每个 token 进来时，Router 只挑其中几个来处理。
仁菜：只挑几个？那总参数量是——
桑多涅：N 乘以单专家参数量——知识量很大。
仁菜：但激活参数量只是被挑中的那几个……推理成本只有总参数的一小部分！
桑多涅：这就是那句核心口号：总参数大，但激活参数小。
仁菜：我打个比方试试——Dense 像一本厚厚的百科全书，你查一个词要把整本书过一遍？
桑多涅：MoE 呢。
仁菜：MoE 像一个图书馆！前台的咨询员听到我的问题，告诉我去三楼的数学专家区就行，不用整个图书馆都搜一遍。
桑多涅：……这个比方能用。Router 就是那个咨询员。现在看具体的数字。
仁菜：DeepSeek 那个？
桑多涅：V3 总参数六千七百一十亿，但每个 token 推理时只激活三百七十亿。
仁菜：六千七百一十亿……激活三百七十亿，那是十八分之一左右？
桑多涅：所以它拿到的是什么。
仁菜：六千七百一十亿的知识量，加上三百七十亿的推理成本——这是 Dense 模型做不到的「学得多加跑得快」！
桑多涅：这个设计哲学，面试官很爱追——现在拆三个组件。第一个，专家。
仁菜：把 Transformer 每层的 FFN 复制 N 份？
桑多涅：结构完全一样，但参数独立——那 N 选多少。
仁菜：越多越好吧？知识量更大——
桑多涅：……这季第几次了。
仁菜：……我错了。那 N 太大会怎样？
桑多涅：每个专家太小、太专门，难以学到通用能力。N 太小呢。
仁菜：专家不够细分……效果就接近 Dense 了。
桑多涅：业界主流：Mixtral 用八个，早期 GShard 六十四个，DeepSeek V3 两百五十六个。
仁菜：那每个专家擅长什么，是预先指定的吗？
桑多涅：……你猜。
仁菜：应该不是？总不能人工规定「你负责数学」吧。
桑多涅：是在训练中自然涌现的——研究者发现训练后的专家会自发分化。
仁菜：分化成什么样？
桑多涅：有的偏向数学符号，有的偏向代码语法，有的偏向常用语言，有的偏向稀有词汇。
仁菜：……没人教它们分工，它们自己分好了。
桑多涅：第二个组件，Router，MoE 最关键的部分。
仁菜：它的结构复杂吗？
桑多涅：通常就是一个简单的线性层——每个 token 进来，Router 看它的 embedding 算出 N 个分数。
仁菜：然后挑分数最高的几个。那挑几个？
桑多涅：最常见的是 Top-K 路由，K 取一或者二。DeepSeek V3 是 Top-8 加一个共享专家。
仁菜：共享专家是什么意思？
桑多涅：不管路由到哪儿，它都参与——负责那些所有 token 都需要的通用能力。
仁菜：哦，就像图书馆的公共阅览区，谁来都能用。
桑多涅：第三个组件，也是训练里最大的坑。
仁菜：什么坑？
桑多涅：专家不平衡——你想想，Router 是学出来的，它会不会有偏好。
仁菜：会……它可能偏爱某几个专家？
桑多涅：然后呢。
仁菜：然后其他专家就……很少被选中？
桑多涅：很少被选中意味着什么。
仁菜：……意味着它们根本没被训过！
桑多涅：而没被训过的专家更差，更差就更不会被选中。
仁菜：恶性循环！最后就变成只有几个专家在干活，其他都是死重。
桑多涅：这叫专家不平衡，是 MoE 训练的著名难题。怎么治。
仁菜：呃……强制平均分配？
桑多涅：那就失去了「专业分工」的意义——工程上是加一个辅助损失。
仁菜：辅助损失？
桑多涅：在主损失之外，额外加一项来惩罚「分配不均」，逼 Router 把 token 摊开一些。
仁菜：所以是在「让它自由分工」和「别让某些专家饿死」之间找平衡。
桑多涅：……这句可以。现在说为什么这么多模型在用它。三条。
仁菜：第一条是训练性价比？
桑多涅：同样算力下训出来的 MoE，效果接近一个大 Dense 模型，但参数总量是 Dense 的好几倍到几十倍。
仁菜：第二条是推理成本可控——每个 token 只用一小部分参数，速度和小 Dense 模型相当。
桑多涅：第三条，可扩展性——要增加模型容量，加专家数比加层数容易。
仁菜：那听起来它全面胜出啊。我们是不是也该——
桑多涅：……停。挑战三条，你先猜第一条。
仁菜：训练难度高？专家不平衡、Router 训不稳。
桑多涅：还有并行化复杂——第二条最要命，跟你的预算直接相关。
仁菜：显存？可它激活的只有三百七十亿啊。
桑多涅：激活是三百七十亿——但推理时，所有专家的参数都要加载到显存。
仁菜：……全部六千七百一十亿都要装进去？！
桑多涅：省的是计算，不是显存。
仁菜：那我们那点卡……根本装不下。
桑多涅：第三条挑战，分布式部署时专家分散在多张 GPU 上。
仁菜：那 token 路由到别的卡上的专家——就要跨卡通信？
桑多涅：通信开销——这在延迟敏感的场景是实打实的代价。
仁菜：……所以它不是免费的午餐。
桑多涅：还有一句得说准——MoE 是这两年最重要的架构方向之一，但它不是唯一答案。
仁菜：Dense 还在用？
桑多涅：很多主力 Dense 模型在生产里依然常见，尤其是中小规模、部署稳定性优先的场景。
仁菜：说「MoE 取代了 Dense」就是说过头了。
桑多涅：……
仁菜：怎么了？
桑多涅：没什么——你去年这个时候，还在问我 Function Calling 是什么。
仁菜：……你居然还记得。
桑多涅：……继续。你们的选型结论是什么。
仁菜：不用 MoE。显存装不下，通信开销我们也扛不住。但我得能讲清楚它为什么好——因为面试官一定会问。
桑多涅：这个判断对——用不上和讲不清，是两回事。
仁菜：那明天组会我怎么讲？
桑多涅：一句话立住核心——不是「拼几个小模型」，是「稀疏激活换便宜推理」。
仁菜：然后三个组件：多个专家、Router、负载均衡。
桑多涅：还有那组数字——六千七百一十亿总参数、三百七十亿激活。它体现的是设计哲学，不是参数表。
仁菜：最后是三条挑战，尤其显存那条——省的是计算不是显存。
桑多涅：这一句能证明你想过部署，不是只读过论文。
仁菜：学费……今天我卡了很久。
桑多涅：哪儿。
仁菜：「省的是计算不是显存」这句——我盯着看了十分钟才反应过来，激活少不等于装得下。
桑多涅：……那你说说，为什么会卡在这儿。
仁菜：因为我一直把「参数量」和「显存」当成一个东西。它俩在 Dense 里确实是一个东西。
桑多涅：MoE 把它们拆开了。
仁菜：……嗯。
桑多涅：这一段当年也卡过我们。
仁菜：「我们」？
桑多涅：……第一批做 MoE 部署的人。整个方向都在同一个地方栽过。
仁菜：所以不是我笨。
桑多涅：是这个东西本来就反直觉——而且你今天说得出「我卡在哪」，这比答对整道题重要。
仁菜：……这句你第七集也说过。
桑多涅：那你现在做到了。明天讲部署——你今天算的显存账，明天要变成真的选型。杨枝甘露。
仁菜：那我今晚把龟苓膏的苦压一压——我是仁菜，我们下集见。
