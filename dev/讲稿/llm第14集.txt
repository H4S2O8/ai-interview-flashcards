llm第14集　KV Cache 是什么？Prompt Caching 的原理是什么？
============================================================

仁菜：欢迎回来，我是仁菜。双皮奶——两碗，冰的。
桑多涅：坐。今天预算怎么样。
仁菜：参数扫完花了一点，百分之九——但我今天来的时候心情很好。
桑多涅：为什么。
仁菜：因为你昨天说，今天讲一个能直接帮我省钱的东西。
桑多涅：……那你先说说你现在怎么理解它。
仁菜：KV Cache 是 Transformer 里的东西，存的是 K 和 V 矩阵。Prompt Caching 是 API 的一个功能，能减少 token 费用。
桑多涅：你只说了表面——KV Cache 具体缓存什么、为了解决什么问题。
仁菜：这个第三集讲过——每次生成新 token 都要重新算前面所有 token 的 attention，KV Cache 就是把算过的存起来。
桑多涅：对了一半——那 Prompt Caching 和 KV Cache 是同一个东西吗。
仁菜：呃……KV Cache 是模型内部的，Prompt Caching 是 API 层面的？
桑多涅：方向对，但差别能讲清楚吗。
仁菜：……讲不清楚。
桑多涅：这个你在 Agent 那边听过一半，今天讲底层。
仁菜：诶？Agent 板块？那是……第一季的事了。
桑多涅：第十二集——你当时问我 Prompt Caching 怎么省钱，我说等你做到工程那一层再讲。
仁菜：……你居然记得。
桑多涅：四季了。今天把这一半补上。先说透 KV Cache——自回归生成的低效到底在哪。
仁菜：每次只产出一个新 token，拼到序列末尾，再对整个新序列重算一遍 attention。
桑多涅：假设你要生成十个 token，第二步在算什么。
仁菜：算 Prompt 加第一个 token 的 attention……
桑多涅：那第一步算的 Prompt 的 attention，和第二步算的，一样吗。
仁菜：……应该一样吧？输入和模型参数都没变。
桑多涅：所以每一步重算前缀，是什么。
仁菜：纯粹的浪费！
桑多涅：算算总账——第 i 步要对 i 个 token 做 attention，复杂度是 i 的平方。全部加起来是什么量级。
仁菜：一加四加九加十六……这个和大概是 N 的三次方？
桑多涅：生成一个一千 token 的回答，等于做十亿次单 token 计算量的运算。
仁菜：十亿次……那还怎么用啊。
桑多涅：所以有了 KV Cache——核心一句话：把前面所有 token 的 K 和 V 缓存起来，每次新 token 只算自己的部分。
仁菜：可是为什么只能缓存 K 和 V？Q 不行吗？
桑多涅：问得好。回到 attention 公式想——新 token 在这个公式里扮演什么角色。
仁菜：它是那个 Q？它在「问」前面所有 token。
桑多涅：那它做点积的对象、加权求和的对象，来自哪儿。
仁菜：K 和 V，都来自前面所有 token。
桑多涅：前面那些 token 的 K 和 V，会因为新 token 的出现而改变吗。
仁菜：……不会！因为 K 和 V 是从已有 token 的 embedding 算出来的，新 token 不影响它们。
桑多涅：所以它们完全可以缓存。而 Q 呢。
仁菜：Q 是新 token 自己的，每次都不一样，缓存了也没用！
桑多涅：这就是为什么叫 KV Cache，不叫 QKV Cache。这个点面试官很爱问。
仁菜：那省下来多少？
桑多涅：每一步只算一个 token 的 K、V，而不是 N 个。总计算量从 N 的三次方降到 N 的平方。
仁菜：一个数量级……所以它不是锦上添花。
桑多涅：是让自回归生成可行的基本盘。所有现代推理框架都默认开着它——vLLM、SGLang、TGI、llama.cpp，没人会关。
仁菜：那它有代价吗？
桑多涅：第三集算过——七十亿模型跑三万二上下文，KV Cache 要多少。
仁菜：十七 GB！加权重十四 GB，一共三十一 GB，一张 RTX4090 放不下。
桑多涅：所以围绕它有一系列优化——PagedAttention、KV Cache 量化、MQA 和 GQA 共享 K 和 V。
仁菜：这些我们前面都碰到过了。
桑多涅：目标都是把这块显存压下来。现在讲第二层——更隐蔽的那个浪费。
仁菜：还有浪费？
桑多涅：KV Cache 解决的是单次生成内的重复计算。但不同请求之间呢。
仁菜：不同请求……
桑多涅：举你们自己的场景——你们客服的 System Prompt 有多长。
仁菜：产品知识、对话规则、Few-shot 示例……大概三千 token 吧。
桑多涅：一天多少次对话。
仁菜：导师说目标是十万次。
桑多涅：那每次请求都从零开始处理这三千 token，重新算三千个 token 的 KV Cache 才能开始生成。
仁菜：十万次乘三千……
桑多涅：三亿个 token 的重复计算。每天。
仁菜：……我们一直在为同一段话付十万遍钱？！
桑多涅：这就是 Prompt Caching 要解决的。核心思路一句话——把 KV Cache 的复用范围，从「单次推理内」扩展到「不同请求之间」。
仁菜：所以第一个请求算完的 KV Cache，在服务器上保留下来？
桑多涅：第二个请求遇到相同前缀，直接跳过计算、复用已有缓存，只算新增的部分。
仁菜：那这两个东西的关系就清楚了——它们是同一套缓存思路，在两个时间尺度上。
桑多涅：说下去。
仁菜：KV Cache 是单次推理内的，同一次生成的不同 token 之间复用；Prompt Caching 是跨请求的，不同请求之间复用相同前缀。
桑多涅：价值上的区别呢。
仁菜：KV Cache 解决的是「让自回归生成可行」……
桑多涅：是 Transformer 推理的基本盘。Prompt Caching 呢。
仁菜：降低 API 成本和延迟——是工程层面的 ROI 优化。
桑多涅：所以 Prompt Caching 不是新发明。
仁菜：是 KV Cache 这个底层机制的工程级延伸！理解了前者，后者几乎是自然推论。
桑多涅：这句话说出来，面试官就知道你不是背功能列表的。那能省多少钱。
仁菜：这个我最关心！
桑多涅：……这里你得说准。Claude 的缓存读取价格可以低到普通输入 token 的百分之十。
仁菜：一折？！那我们那三亿 token——
桑多涅：别急着算——OpenAI 等平台也有自己的缓存折扣，规则各不一样。
仁菜：那我该怎么说？
桑多涅：说「不同厂商的计费规则不一样」。别报一个固定比例当行业标准。
仁菜：延迟呢？也能省？
桑多涅：能，但也别死记一个数——延迟收益和前缀长度、命中率、服务端负载都有关。
仁菜：……这一季我第几次听你说「别死记一个数」了。
桑多涅：这个板块全是这种东西——最后说工程要点，这条最实用。
仁菜：你说。
桑多涅：固定内容在前，动态内容在后。
仁菜：为什么？
桑多涅：你自己想——缓存命中的条件是什么。
仁菜：前缀相同……
桑多涅：那要是你把用户的问题放在 System Prompt 前面，会怎样。
仁菜：每个用户的问题都不一样——那前缀就永远不同，缓存永远不命中！
桑多涅：还有一条更狠的：前缀只要差一个字符，就是 miss。
仁菜：一个字符？！那要是我在 System Prompt 里加了个时间戳——
桑多涅：恭喜，你的缓存命中率是零。
仁菜：……我们上周的模板里真的有一行「当前时间」。
桑多涅：那你回去看看它在第几行。
仁菜：……第二行。
桑多涅：……
仁菜：我这就去改。
桑多涅：改完把命中率量一遍，这就是你今天的学费。
仁菜：那明天组会我怎么讲这道题？
桑多涅：先说它们是同一套机制在两个时间尺度上。再说 KV Cache 为什么只缓存 K 和 V，不缓存 Q。
仁菜：然后说 Prompt Caching 是跨请求复用前缀，价值在成本和延迟。
桑多涅：最后落到工程要点：固定在前、动态在后，差一个字符就 miss。这一句能证明你真上线过。
仁菜：学费——我先报个估算：三千 token 的 System Prompt，一天十万次，缓存前是三亿 token 的重复计算。改完模板我再报真实命中率。
桑多涅：……这算数据。但记得报的时候说明这是估算，不是实测。
仁菜：知道啦。诶，等一下。
桑多涅：嗯。
仁菜：第一季第十二集……你那时候就想到我会做到这一层？
桑多涅：……我只是不喜欢讲一半。
仁菜：……
桑多涅：明天讲量化——你今天省的是算力，明天省的是显存。马拉糕。
仁菜：那我今晚先去改模板！我是仁菜，我们下集见。
