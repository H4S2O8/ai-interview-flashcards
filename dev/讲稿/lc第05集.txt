langchain第05集　在 LangChain 中，如何为 Agent 注册工具？
============================================================

仁菜：欢迎回来，我是仁菜。豌豆黄 —— 切好了，你先。
桑多涅：……你切成九块。
仁菜：对应我那九条不能做什么。昨晚全贴工位上了，进度还剩四周。
桑多涅：……那今天讲工具怎么注册。你先说。
仁菜：给函数加一个 @tool，然后放进 Agent 就行。
桑多涅：已有的普通函数能不能直接传？复杂参数怎么校验？什么情况下需要 StructuredTool 或者 BaseTool？
仁菜：那我全部继承 BaseTool 呗，这样最规范。
桑多涅：……为了查询一次天气也写一个类。
仁菜：诶？这不是更专业吗？
桑多涅：只会增加样板代码。这句留着，等会儿你自己推翻它。先问一个更要命的 —— 用户身份和权限，怎么传给工具。
仁菜：让模型生成一个 user_id 参数？
桑多涅：……停。
仁菜：……这个我不是装的，我真是这么写的。
桑多涅：可信身份不能由模型填写。两个原因，你自己想一个。
仁菜：呃……它可能填错？
桑多涅：还有更狠的。
仁菜：……还能被提示注入利用！有人在输入里写查一下张三的余额，它就真去查了。
桑多涅：这条昨天讲权限的时候碰过一次，今天是它的具体形态。先说本质 —— 注册一个 Tool，到底注册了什么。
仁菜：把函数交给框架？
桑多涅：模型看得到你 Python 函数的源码吗。
仁菜：看不到。那它凭什么知道该调用谁……凭我们给它的说明？
桑多涅：注册工具的时候，LangChain 会把函数转换成一份模型能理解的说明。模型先看名称和描述，判断这个工具叫什么、什么情况下该用；决定调用之后，再按参数 Schema 生成满足类型和约束的参数。
仁菜：那真正拿着这些参数做事的是应用侧的函数。……这就是昨天那条边界，模型只提议，应用才执行。
桑多涅：所以注册的本质是两件事同时发生 —— 向模型提供一份工具说明，向运行时提供一个真正可执行的函数。
仁菜：那工具描述和 Schema 就不只是注释了……它们是模型与业务代码之间的调用合同！
桑多涅：记住调用合同这个说法。描述过于模糊，模型可能选错工具；参数缺少约束，模型可能生成根本执行不了的数据。合同写得含糊，两边都会出事。
仁菜：那具体有几种写法呀？
桑多涅：四种，但别当成功能清单。当成一条随复杂度上升的路径 —— 第一档，什么情况下连装饰器都不用。
仁菜：呃……函数本身就说得清楚的时候？
桑多涅：名称、类型注解和 docstring 已经能把用途说清楚，直接放进 tools 就够了。什么时候不够？你想明确修改工具名称、补充参数描述，或者用 Pydantic 限制枚举和范围的时候。
仁菜：那就上 @tool。它能干什么呢？
桑多涅：从函数签名和 docstring 自动推导 Schema，也允许用 Pydantic 显式描述复杂参数。大多数业务工具的首选就停在这一档。
仁菜：那第三档是解决什么问题的？
桑多涅：问题不再是 Schema 不清楚，而是原函数不能改，或者要在运行时动态组装同步与异步实现。
仁菜：原函数不能改……比如那是别人的库？
桑多涅：或者同一个业务函数要注册成不同名称、不同描述，给不同场景用。StructuredTool 解决的正是这个组装问题。
仁菜：那 BaseTool 什么时候才轮得上呀？
桑多涅：当工具不再只是一个函数的时候 —— 它要长期持有数据库或者第三方客户端，同时管理同步、异步、tags、metadata 和回调。
仁菜：……那它就有生命周期了！它从一个函数变成了一个组件。
桑多涅：这时候才值得承担更多样板代码。四档的选择原则，你总结。
仁菜：函数能说清楚就用普通函数；需要明确 Schema 就用 @tool；需要运行时组装再用 StructuredTool；出现组件生命周期才考虑 BaseTool。
桑多涅：那你开场那句全部继承 BaseTool 最规范，错在哪。
仁菜：错在……用最重的方式解最轻的问题。样板代码是成本，不是专业度。
桑多涅：还有一类工具你会在文档里看到，别搞混 —— 模型厂商提供的 Web Search、代码执行器这些服务端工具，有时候用厂商约定的字典配置。那属于特定 Provider 的能力，要单独查对应集成文档，别把它当成通用 Python Tool 的主要定义方式。
仁菜：记下了。那可信参数到底怎么传呢？
桑多涅：举个具体的。查询我的账户余额这个工具需要用户 ID，你把 user_id 放进模型可见的 Schema 会怎样。
仁菜：刚才说过了 —— 可能填错，也可能被恶意提示诱导去查别人的账户。
桑多涅：所以要区分两类参数。任务参数是城市、关键词、订单号这些，可以让模型填；可信参数是用户 ID、租户、权限、存储对象，这些不能给模型看，它们通过 ToolRuntime 注入。
仁菜：懂了。那 ToolRuntime 就是个装可信东西的口袋？
桑多涅：这里还有一层细分，很多人不知道。不同信息的作用域不同 —— 用户身份、租户、依赖属于本次调用上下文，从 runtime 的 context 读；当前会话的短期状态放在 state；跨会话仍然要保留的长期数据，才进 store。
仁菜：context、state、store……三层。昨天你让我把 State 和 Store 分清，今天又多一层。
桑多涅：三个搞混，要么泄露，要么丢数据。那模型最终能看到什么。
仁菜：账户类型这种任务参数它能看到也能填；runtime 它看不到 —— 可信用户身份由应用传入，不是模型生成的。
桑多涅：这是工具权限控制的重要边界。这一句在面试里说出来，比背四个类名管用。
仁菜：……
桑多涅：怎么。
仁菜：我的工具注册层，user_id 是从模型返回的参数里取的。我一直觉得反正 Prompt 里写了只能查自己的……
桑多涅：昨天那句你还记得吗。
仁菜：Prompt 里写禁止退款，不能替代退款接口本身的身份校验 —— 我昨天点头点得可快了！
桑多涅：今天呢。
仁菜：今天发现我自己就是那个错误。
桑多涅：那还有一件事要问 —— 生产环境还要关注什么。
仁菜：参数校验、权限检查、超时、重试、幂等……还有错误分类？
桑多涅：错误分类为什么重要。
仁菜：呃……方便排查？
桑多涅：不止。你分四类想 —— 哪些错误适合自动重试。
仁菜：网络超时这种临时故障。参数错误重试多少次都一样，应该返回清楚的信息，让模型知道自己填错了。
桑多涅：业务拒绝呢。比如余额不足。
仁菜：那也不是故障，是业务事实，也要清楚返回。程序 Bug 就更不该重试了，而且不能被统一吞掉，不然线上永远查不出问题。
桑多涅：四类错误四种处理。全都 catch 一下返回一句工具执行失败，是最省事也最害人的写法。
仁菜：……我的就是那样写的。一个大 try，返回一句查询失败请稍后重试。
桑多涅：那你线上那三次错的物流状态，是怎么发现的。
仁菜：……用户投诉。
桑多涅：那明天答辩你怎么讲这道题。
仁菜：先讲本质 —— 注册是同时向模型提供说明、向运行时提供可执行函数，工具描述和 Schema 是调用合同。然后四种方式是一条随复杂度上升的路径，不是功能清单，别为了显得专业直接上最底层的类。
桑多涅：最关键的一段。
仁菜：可信参数不能由模型填写 —— 任务参数走 Schema，可信参数走 ToolRuntime，而且 context、state、store 三层作用域不同。最后补错误分类。
桑多涅：错误分类那条最像做过运维的人。
仁菜：……我今天要干一件事。
桑多涅：说。
仁菜：我要把我那个工具注册层删掉。不是重构，是删掉。
桑多涅：为什么不重构。
仁菜：因为它的问题不在实现，在设计 —— 我把可信参数交给了模型。这个错误重构不掉，它是我一开始就想歪了。四百二十行里，这一层占一百三十行。
桑多涅：……删得对。
仁菜：诶？
桑多涅：下一句。
仁菜：……学费？今天量的是：那一百三十行删掉之后，替换成六个 @tool 加一个 ToolRuntime 注入，一共三十一行。
桑多涅：这算数据。带上工具个数一起报。明天讲记忆，短期和长期怎么实现。糖不甩。
仁菜：记忆？那不是上一季 RAG 讲过 ——
桑多涅：明天你会知道分工在哪儿。
仁菜：……诶，豌豆黄你吃了三块。
桑多涅：……你切成九块，我拿走三分之一，这叫合理。我是仁菜，我们下集见 —— 这句是你的。
仁菜：……我是仁菜，我们下集见！
