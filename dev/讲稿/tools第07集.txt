tools第07集　Function Calling 也属于工具调用，请问什么场景下使用 Function Calling，什么场景下使用 MCP？
============================================================

仁菜：欢迎回来。我是仁菜。水果挞，我自己挑的 —— 你昨天说花哨，我倒要让你尝尝，花哨可以很好吃。
桑多涅：……水果倒是新鲜。勉强过。五天。上集结尾你把选型说成了三句话，今天把那三句长成完整的一棵决策树 —— 这题面试里是送分题，也是送命题。
仁菜：送分我知道，这题答起来痛快：小项目用 Function Calling，大项目用 MCP，看项目规模就完了。
桑多涅：送命就送在这。项目规模大，就一定要用 MCP？
仁菜：大项目……工具多啊。
桑多涅：要是一个大项目，工具全在内部用，谁都不复用呢？
仁菜：呃……那确实也不用 MCP。
桑多涅：你看，规模这一刀下去就切错了。
仁菜：那我换个维度！看工具数量 —— 工具少用 Function Calling，工具多上 MCP，MCP 能自动发现，总对了吧？
桑多涅：数量是个因素，不是唯一的。我问你：社区里已经有现成的 MCP Server 了，你只需要其中一个工具，你还手写 Function Calling 去对接一遍 API 吗？
仁菜：……不，直接配置上用。
桑多涅：你看，数量这一刀也切错了。
仁菜：又双错……那到底看什么，维度全摆出来吧。
桑多涅：先摆本质。上集那句「管嘴管门」还记得吧，今天再往下挖一层：Function Calling 的工具是内嵌的 —— schema 和调用逻辑直接写在你应用代码里，工具和应用长在一起，应用换了就跟着重写；MCP 的工具是独立的 —— 封成独立进程，对外标准接口，生命周期完全和应用解耦，应用死了它还能活着被别人用。
仁菜：内嵌，独立。一个长在身上，一个住在外面。
桑多涅：这四个字定了调，场景就好挑了。先说什么时候 Function Calling 就够 —— 记住四个场景。第一，快速原型和 Demo：目的是跑通想法，直接代码里写 schema 和调用逻辑，为一个原型搭一套 Server，搭架子的时间比原型本身还贵。
仁菜：第二我猜 —— 工具只有这一个应用用？
桑多涅：对。最典型：查本公司私有数据库的接口，除了这个应用谁都不碰它。逻辑写在项目里最清晰，何必额外养一个进程。第三，需要对执行逻辑做精细控制的：权限校验、参数二次加工、特殊的错误处理、调用链路追踪 —— 全在你自己代码里，想怎么嵌怎么嵌。MCP 的 Server 是独立进程，这类定制要跨进程传递约定，麻烦得多。
仁菜：第四呢？这三个我都能猜到，第四个肯定是你藏着的。
桑多涅：部署环境的限制。有些受限的云环境、Serverless 平台，压根不允许你启动子进程 —— stdio 模式的 MCP Server 直接没法跑。这时候退回 Function Calling，工具全写在主进程里，反而最稳。
仁菜：……Serverless 连子进程都不让起，这个我真不知道。这条记下了。那 MCP 那边呢？
桑多涅：一句话定调：只要工具不是「自己用、用一次就扔」，MCP 都值得考虑。核心场景三个。第一，跨项目跨团队复用：同一套 GitHub 工具，你自己的 Claude Desktop 用、同事的 Cursor 用、团队的持续集成 Agent 也用 —— Function Calling 就是三处各养一份，接口一变三处同步改；MCP 是 Server 那一侧改一次，所有客户端自动受益。
仁菜：第二是现成的，你刚才已经用这个打过我脸了 —— 社区有官方 Server，直接配，别造轮子。
桑多涅：第三，规模。这里我要先纠一个你迟早会说的错：不存在「超过几个就必须上 MCP」这种数字门槛。看的是三样东西揉在一起 —— 工具的复杂度，schema 是几行还是几十行；团队规模，一个人维护还是几个人都在碰；变更频率，接口三天两头改还是一年不动。五个又复杂又常改的工具，很快把你拖进泥潭；两个极简又不动的，犯不着。
仁菜：那这个度怎么拿？
桑多涅：没有度，有个拐点 —— 你哪天打开项目，发现工具定义散落在四个文件夹里，谁也说不清一共几个，那就是拐点到了，感觉比数字准。最后一条：做正式的 Agent 系统，MCP 几乎是必选。Agent 的工具来源杂、数量大，schema 散在代码各处就是灾难；MCP 让它按需连 Server，新增工具不用动主程序。
仁菜：那这题的答题模板 —— 不是，决策树，长什么样？
桑多涅：五问，依次过。第一问，社区有现成 Server 吗？有，直接用，收工。第二问，工具要在多个项目或多人之间复用吗？要，MCP。第三问，数量、复杂度、团队、变更频率综合看，摸到散乱的拐点了吗？到了，MCP 统一管理。第四问，做的是正式系统还是原型？正式系统偏 MCP，原型偏 Function Calling。第五问，部署环境让不让起子进程？不让，Function Calling 保命。
仁菜：五问……第一问直接抄近道，第五问一票否决，中间三问看处境。那我总结成一句：只用自己、只用一次、不需要复用，Function Calling；其他情况优先考虑 MCP。
桑多涅：对，还能再补一层：它俩不是竞争关系，MCP 底层本来就是 Function Calling 驱动的 —— 选哪个看工程需求，不看技术优劣。
仁菜：诶，那我再抬个杠：Function Calling 写在代码里多直观啊，配置文件、进程、协议那么绕 —— 是不是干脆都别用 MCP 了？
桑多涅：……上集你说「全上 MCP」，这集你说「全别用」。你的意见跟风扇似的，上集吹东这集吹西。
仁菜：哎呀 —— 我这不是举一反三嘛！
桑多涅：你这是举一反三的反面。这题面试官想听的就是「取舍」，单维度一刀切，切哪边都是雷。规模是雷，数量是雷，全上是雷，全不上还是雷。
仁菜：四面都是雷，那不站中间就行了……好啦好啦，我过一遍：本质是内嵌和独立；Function Calling 四场景 —— 原型、私有独用、要精细控制、环境不让起子进程；MCP 三场景 —— 复用、现成 Server、规模拐点，外加 Agent 必选；决策树五问，从抄近道到一票否决；核心一句，只用一次自己用的才 Function Calling，其他优先 MCP，选型看工程需求不看技术优劣。
桑多涅：今天没有磕绊，只有那个风扇。
仁菜：风扇也是成长的一部分！下集预告：一个冷门题 —— 为什么有些推理模型不支持 MCP？说实话我连问题都没读懂，推理模型跟 MCP 还能打架？甜点你点，我下班了。我是仁菜，我们下集见。
桑多涅：焦糖布丁烧。明早带，别买隔夜的。
