第 8 集　请你介绍一下 AI Agent 的记忆机制，并说明在实际开发中应该如何设计记忆模块？
============================================================

仁菜：第八集。桑多涅，我今天……还没来得及买甜点。
桑多涅：我知道。
仁菜：啊？
桑多涅：你昨天在群里说模拟面试的题库范围出来了，记忆是必考。所以我就来了。
仁菜：……你是特地为这个来的？
桑多涅：我是顺路。开始吧，这题原文最长，别浪费时间。
仁菜：好、好。那我先说 —— 记忆分短期和长期两种。
桑多涅：不够。完整是四层，从最短暂到最持久。
仁菜：四层？
桑多涅：第一层，感知记忆，当次调用的原始输入，最短暂。第二层，短期记忆，context window 里的 messages，维持当前任务状态。第三层，长期记忆，存在外部数据库、跨任务持久化的内容。第四层，实体记忆，从对话中提炼出的结构化事实，信息密度最高。
仁菜：实体记忆和长期记忆有什么区别？
桑多涅：长期记忆存的可能还是一段原始文本，实体记忆是提炼过的结构化事实。比如对话里聊了半天，提炼出「这个用户偏好 Python、不接受全局变量」这样一条 —— 密度完全不一样。
仁菜：懂了。那设计记忆模块，难的是什么？
桑多涅：三个核心问题：存什么、怎么存、什么时候取出来用。这三个问题背下来，这题的骨架就有了。
仁菜：先说存什么。
桑多涅：只存对下次任务有价值的内容，过滤噪音。这句听着简单，做的时候最容易失控 —— 什么都往里塞，检索出来的噪音会淹没有用的信息。
仁菜：怎么存呢？
桑多涅：语义内容用向量数据库，结构化偏好用关系数据库，混合存储是主流。别一听记忆就只想到向量库。
仁菜：什么时候取？
桑多涅：两种策略。任务开始前主动检索，加载背景；执行过程中按需检索特定知识。前者是「先把该知道的都调出来」，后者是「用到了再查」。
仁菜：那这三个问题串起来是什么？
桑多涅：读、用、写，三阶段闭环。任务前读出相关记忆，执行中用，任务后把值得留的写回去。用这个闭环收尾，这题的结构就完整了。
仁菜：那有个实际问题 —— 短期记忆的 context window 塞满了怎么办？
桑多涅：三种思路，从简单到复杂。最简单的是滑动窗口，只保留最近 N 轮对话，更早的直接丢弃。实现简单，代价是早期的重要信息可能被丢掉。
仁菜：有多严重？
桑多涅：举个真实会遇到的场景：用户在第一轮说「所有代码用 TypeScript」，到了第十轮这条信息被滑出窗口了，Agent 又开始写 JavaScript。用户会很崩溃。
仁菜：那第二种？
桑多涅：摘要压缩。当历史长度接近上限时，用 LLM 把早期的对话历史压缩成一段摘要，替换掉原始的冗长历史。token 占用能从几千降到几百，关键信息保留。代价是压缩过程本身会丢失细节，而且需要额外的 LLM 调用。
仁菜：第三种呢？
桑多涅：把不常用但重要的信息「卸载」到长期记忆里。执行过程中产生的中间结果，如果当前步骤不需要但后面可能用到，就先存到向量数据库里、从 context window 中移除，等后面某步需要时再检索回来。
仁菜：相当于给工作台配了个抽屉。
桑多涅：桌面放不下的东西先收到抽屉里，要用的时候再拿出来。这个比喻可以用。
仁菜：这些都要自己实现吗？
桑多涅：有现成的。最近两年出现了一些专门为 Agent 记忆设计的开源框架，其中社区最活跃的之一叫 Mem0，GitHub 上五万星以上。
仁菜：它做什么的？
桑多涅：把记忆管理做成一个独立的服务层。你只需要调 memory.add 存记忆、memory.search 查记忆，底层的 embedding、去重、冲突消解它全帮你做了。面试时能提一句，说明你关注生态而不只是看论文。
仁菜：那记忆存进去之后，是不是就是一条条孤立的文本？
桑多涅：……你这个问题问得比我预想的早。
仁菜：问错了吗？
桑多涅：问对了。这正是纯向量检索的局限 —— 它是一条一条地存、一条一条地取，记忆之间没有关联。但很多时候，信息之间的关系和信息本身一样重要。
仁菜：举个例子？
桑多涅：你存了「用户 A 是公司 B 的 CTO」和「公司 B 的主营业务是云计算」这两条。现在问「用户 A 所在的公司做什么业务」，纯向量检索可能检索不到 —— 因为这两条记忆的文本相似度并不高。
仁菜：那怎么办？
桑多涅：知识图谱。用「实体、关系、实体」的三元组结构存储信息。「用户 A 担任 CTO 于公司 B」是一个三元组，「公司 B 主营业务是云计算」是另一个。实体和实体之间通过明确的关系连接，形成一张网。
仁菜：然后就能沿着网走？
桑多涅：查询时可以沿关系链做多跳推理，这是知识图谱最厉害的地方。刚才那个问题：从「用户 A」出发，沿「担任 CTO」找到「公司 B」，再从「公司 B」沿「主营业务」找到「云计算」—— 两跳就拿到了答案。
仁菜：这个向量检索确实做不到。
桑多涅：还有最后一个问题：记忆用久了会变脏。
仁菜：变脏？
桑多涅：同一个主题可能存了十几条不同时间的记忆，有些内容重复，有些已经过时，有些甚至互相矛盾。不做整理的话，检索时噪音越来越大，有用的记忆被淹没在无用的碎片里。
仁菜：那要定期清理？
桑多涅：叫记忆整合，三个环节。第一，去重 —— 把语义相近的多条合并成一条更完整的版本。比如「用户喜欢简洁的代码」「用户说过代码要精简」「用户要求不要冗余」，其实是同一个意思，合并成一条就够了。
仁菜：第二个环节？
桑多涅：冲突消解 —— 两条记忆互相矛盾时，保留时间更新的那条，标记旧的为过期。比如之前存了「用户偏好 Python」，后来他说「最近转用 Go 了」。
仁菜：那怎么知道哪条更新？
桑多涅：时间戳。这里时间戳非常关键，没有它你根本无法判断哪条是最新的。这是个很容易在设计时漏掉的字段。
仁菜：第三个环节？
桑多涅：最有价值的一个，叫抽象提炼。本质是把情节记忆转化为语义记忆。
仁菜：这两个词上上集讲过 —— 情节记忆是具体经历，语义记忆是事实性知识。
桑多涅：记得不错。举个例子：Agent 三次遇到爬虫任务，第一次发现某个简单请求库被反爬拦住了，第二次发现页面是 JavaScript 渲染的、拿到的是空页面，第三次又碰到动态加载。这三条单独看都是独立的事件记录。
仁菜：但放一起看就有规律了。
桑多涅：把它们提炼成一条：「当目标网站有动态渲染时，基于 HTTP 的简单请求库往往拿不到完整内容，需要用浏览器自动化工具」。这条语义记忆的价值，远高于三条零散的经历。
仁菜：这就是从经验里长出方法论。
桑多涅：这题答到这儿就很完整了。四层分类、三个核心问题、读用写闭环，再加上 context 管理、知识图谱和记忆整合，面试官很难追问倒你。
仁菜：桑多涅，谢谢你今天特地过来。
桑多涅：我说了是顺路。下次记得买甜点。
仁菜：下一集我们更细地讲记忆怎么存、粒度多少、怎么用。我是仁菜，我们下集见。
