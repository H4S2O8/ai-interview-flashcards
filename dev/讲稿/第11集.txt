第 11 集　Multi-Agent 的架构拓扑有哪些？Single 还是 Multi 该怎么选？
============================================================

仁菜：第十一集。桑多涅，今天是可露丽。
桑多涅：上一集说了，今天考判断力。第一个问题：多个 Agent 之间怎么组织？
仁菜：两种吧 —— 有一个头儿统一指挥，或者大家平等地互相通信。
桑多涅：术语上叫中心化 Orchestrator 模式和去中心化 Peer-to-Peer 模式。工程上几乎都选前者，为什么？
仁菜：因为……好管？
桑多涅：三个字：可控、可追踪、出了问题能顺着调度链路排查。所有任务分配都经过一个中心节点，你知道每个子任务派给了谁、什么时候派的、结果是什么。
仁菜：那去中心化听起来更灵活啊，为什么生产上不用？
桑多涅：三个致命问题。第一，任务分配没有协调 —— 可能两个 Agent 同时抢一个任务，也可能一个任务谁都没接。
仁菜：第二个？
桑多涅：执行顺序没有保证。谁先谁后取决于消息到达的时序，同样的输入跑两次可能是不同的执行路径，问题根本没法复现。
仁菜：第三个。
桑多涅：失败没有感知。一个 Agent 挂了，没有人知道 —— 因为没有中心节点在等它的结果。整个系统就那么静静地卡住了。
仁菜：这三个都是生产环境的死穴。
桑多涅：所以「去中心化更灵活」这句话在论文里成立，在线上不成立。面试时能主动说出这三点，比背两个拓扑名词强。
仁菜：那 Orchestrator 具体怎么做？
桑多涅：三种变体，复杂度递增。第一种叫静态路由 —— 分配规则预先写死，代码任务给 Coder，搜索任务给 Researcher。简单、可预测。
仁菜：第二种？
桑多涅：动态规划。Orchestrator 本身就是一个 LLM，根据输入动态生成任务计划，执行中也可以调整。
仁菜：第三种？
桑多涅：自适应编排。它还会根据 Worker 的执行结果实时调整后续计划 —— 比如搜回来的信息不够，就追加一轮搜索。
仁菜：那是不是应该都用第三种？最强。
桑多涅：……你看，这就是判断力的问题。
仁菜：不该用吗？
桑多涅：大多数场景用动态规划就够了。自适应编排更强，但调试复杂度高很多 —— 计划本身在不停变，你连「它为什么这么走」都很难复现。工程上，能力和可维护性要一起算。
仁菜：我又犯了那个毛病，一看到更强的就想选。
桑多涅：这个毛病面试官特别爱抓。接着：Orchestrator 和 Worker 各自的职责是什么？
仁菜：Orchestrator 分配任务，Worker 干活。
桑多涅：太粗。Orchestrator 不做任何具体工作，只负责三件事：读懂大目标并拆成子任务、判断每个子任务交给谁、收集产出拼成最终答案。
仁菜：Worker 呢？
桑多涅：Worker 只关注自己那一块 —— 不需要知道整体任务是什么，也不需要知道其他 Worker 在做什么，拿到自己的输入就干自己的活。
仁菜：这个边界为什么重要？
桑多涅：因为它决定了 context 隔离能不能成立。Worker 一旦需要知道全局，它的 context 就得装全局信息，你上一集讲的隔离优势立刻消失。
仁菜：原来这两讲是这么连起来的。
桑多涅：那么最关键的问题来了：什么时候才该上 Multi-Agent？
仁菜：任务复杂的时候？
桑多涅：三类场景，具体一点。第一，context 要撑爆了；第二,需要不同的专业分工；第三,有子任务可以并行。不属于这三类，就用 Single-Agent。
仁菜：盲目上 Multi 会怎么样？
桑多涅：只增加系统复杂度，带不来对应收益。多一个 Agent 就多一层通信、多一处可能出错的地方、多一份调试成本。
仁菜：有没有更好用的判断方法？面试的时候脑子容易乱。
桑多涅：两个问题就能定。第一问：Single-Agent 能搞定吗？流程明确、不太长、不需要多种专业分工，就用 Single，别为了显得高级而引入 Multi。
仁菜：第二问？
桑多涅：确实超出 Single 的边界了，再问：你能接受系统行为不可控吗？
仁菜：生产环境肯定不能接受。
桑多涅：所以答案几乎一定是中心化 Orchestrator。两问下来，选型结论就出来了，而且推理链条是清楚的 —— 面试官看的是这个过程，不是结论本身。
仁菜：桑多涅，我问一个跟技术无关的。
桑多涅：……说。
仁菜：你其实挺忙的吧。为什么愿意每周花时间陪我讲这些？
桑多涅：……蛋糕。
仁菜：真的？
桑多涅：还有 —— 你问问题的方式在变。第一集你问的是「这是什么」，现在你会问「为什么不是另一种」。
仁菜：这算夸奖吗？
桑多涅：这算事实陈述。可露丽我带走了。
仁菜：下一集讲记忆压缩，context 塞满了到底怎么办。我是仁菜，我们下集见。
